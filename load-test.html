The load test

We played a whole pickup week against the real server, with 360 students, 6 volunteers and the coordinator all using it at the same moment. It found one serious problem: at 5 pm, the app froze and nobody could log in or book. That's fixed now, and the same test passes with no errors and no broken rules.

A record of the load test runs of 12 November, with the hours of the time. The food bank's real hours, from 13 November, are Monday and Thursday 3:30 to 7:30 pm, with no-shows at 8 pm. The times below are kept as they were then.

Sending lots of requests at once, like real busy moments, to see if the server stays fast and correct. The 559 tests we had check one thing at a time. A load test checks what happens when everything happens together.

An open line from the server to PostgreSQL. A request needs one to read or save anything. The app keeps 15 open and lends them out. That's called the pool.

How the test works

The test is in backend/loadtest/. It does four things:

  1. Fills the test database with the sample food, the coordinator Alex, 6 volunteers, and 360 made-up students who already have passwords. It never touches the working database.
  2. Starts the real server, with the same code, the same locks and the same database pool as in real use. Only the clock is moved, like the demo does, so the server thinks it's Sunday at 4:59 pm, or Monday at noon.
  3. Plays each person with their own login, sending the same requests their browser would. Everyone waits at a starting line, then goes at the same moment.
  4. Checks the database after each phase for broken rules. It also checks that the database agrees with what each person was told. If a student saw "Booked! Your code is K3P", that booking must really be there.

Anything that goes wrong is listed at the end: a server error (a "500"), a request with no answer, or a broken rule.

What it found: the 5 pm freeze

Before the fix

0 of 370 students could log in. The pickup times page timed out 2,520 times. Nobody booked anything, and the coordinator couldn't close Thursday. Even a normal hour of browsing froze, with answers taking about 60 seconds. The server log shows 1,378 times a request gave up waiting for a database connection.

The data was never wrong. Every rule held. The app just stopped answering.

Why it froze

Our routes are written as plain def, so FastAPI runs each one on one of its 40 threads. A request borrows a database connection with its first query, and gives it back only when its session is closed. Here's the catch: before the session is closed, FastAPI checks the answer (for example, that the booking has a code), and that check needs a free thread too.

A small story. At 5:00 pm, 360 students press Log in.

The first 15 get connections, check their passwords and finish. Each now needs a thread to check its answer.

But the other 345 are queued for threads, and the first 40 of them already have one. Each of those 40 sits on its thread, waiting for a connection.

The 15 connections are held by requests waiting for threads. The 40 threads are held by requests waiting for connections. After 30 seconds, the waiting requests give up with an error, and the next 40 do exactly the same.

It needed a real crowd to show up. With one person at a time, which is all the normal tests do, it can never happen.

The fix

1. A queue at the door

app/door.py lets only 15 requests into the app at once, the same number as there are connections. The others wait in a line before they take a thread. Every request inside can always get a connection, finish, and leave, so the next one in line comes in. Waiting in the line costs no thread and no connection, and usually only a few milliseconds.

Like a shop with 15 baskets. The doorman lets in one shopper for each free basket. Without him, 40 people crowd the aisles waiting for a basket, and the people holding baskets can't get to the till.

The number is a setting, DB_CONNECTIONS (15 unless backend/.env says otherwise). The database pool uses that same number, with no extras, and a test checks they match. If they ever didn't, the freeze could come back.

2. At most 4 password checks at once

Each argon2 check needs 64 MB. With 15 at once, the server peaked at 1.1 GB, enough to crash a small cloud server with 1 GB. Now app/security/passwords.py runs at most 4 checks at a time, which needs at most 256 MB. Logging in isn't slower: argon2 is limited by how fast the memory is, so 15 checks at once each take about 4 times longer anyway.

What else we could have done, and why not

Other wayWhy not
More database connections, like 40 or 100It only moves the line. A crowd of 101 freezes it again. Cloud databases also limit connections; small plans often allow only about 25.
Fewer threads, the same number as connectionsA request keeps its connection even after it lets go of its thread, while it waits for its answer to be checked. So it can still happen, just less often.
Rewrite every route as async defThe answer check would then run without a thread. But every database call would have to change too: hundreds of lines, and new ways to make mistakes, for the same result.
Give the connection back before the answer is checkedEvery route would need extra code to remember this. One forgotten route brings the freeze back. The door fixes all routes in one place.

Two harder runs

20 places per time instead of 1

The food bank's setting of 1 place per time gives only 12 places a day, so only 12 bookings were made. With 20 places there were 240, so lots of students fought over the same times and the same food at once.

  • 238 booked: everyone told "booked" has exactly one booking, and nobody else does.
  • No time over its places, and no food counted wrong, after 625 presses of Book. Of the 30 students who pressed Book twice, none got two bookings.
  • 202 bags handed over, each once. A code typed at two counters gave one "handed over" and one refusal.
  • 36 no-shows, each marked once, even with two jobs runs at the same moment. The second run said "Another jobs run is still going" and did nothing, as it should.
One CPU core, like a cheap cloud server

No errors, and every rule held. One slow spot: 370 logins at once took up to 87 seconds, because each password check is slow on purpose and one core does them one after another. That only happens on a night when everyone logs in at once. Students stay logged in for 30 days, so most won't. Even so, a host with 2 CPU cores is the safer choice.

What this test doesn't show

  • Everything ran on this PC, with the database on the same computer. On a cloud, each database query also travels over the network, so answers are a little slower.
  • It ran one server process. A host can run several, with --workers, which the test can try too. Each one uses DB_CONNECTIONS connections, so the database must allow that many for every process, plus a few for the jobs script.
  • Logins and bookings happened one after the other, not at the very same moment.
  • The 5 pm rush is real: with 1 place per time, 288 of 300 students saw "no times left" within seconds. The system handled that correctly. It's the known issue in CONSTRAINTS.md, now with numbers.

Running it yourself

From backend/. It empties the test database, like the tests and the demo do.

.venv\Scripts\python -m loadtest.run                  the run on this page
.venv\Scripts\python -m loadtest.run --capacity 20    20 places per time
.venv\Scripts\python -m loadtest.run --one-core       a small cloud server
.venv\Scripts\python -m loadtest.run --workers 4      four server processes

It takes about 3 minutes. The last line says "No problems" or lists each one. The saved runs are in backend/loadtest/results/, and the server's own log of each run goes to backend/loadtest/server.log.
