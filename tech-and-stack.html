3How one booking travels through the system

Ana presses Book on Sunday at 5:08 pm. Here is every stop on the way, and what each one checks.

1Ana's phone (React) sends POST /bookings with her held slot, items and substitutes. Her login cookie goes with it automatically.
↓
2FastAPI finds the Python function for POST /bookings.
↓
3Login check: the cookie says this is Ana's account. If she isn't logged in, she sees "please log in". P6
↓
4Pydantic checks the shape: items is a list of at most 13, substitutes at most 5. If something's wrong, she gets an error, and the error never repeats her ID number back. P10
↓
5Booking rules (plain Python): is booking open? 28 days? no other booking? didn't cancel for this day? is the hold still hers? S5 F1 F2 S6 S8 you write this
↓
6SQLAlchemy → PostgreSQL, one transaction: lock the slot, take each item off the stock count (never below zero), save the booking. If the code missed anything, the database's own rules stop it. S2 I4 B4 you write this
↓
7Back to Ana: "Booked. Your booking code is K3P."

Why check the rules twice, in step 5 and again in step 6? Step 5 gives Ana a clear message ("28 days haven't passed yet"). Step 6 is the safety net: even if step 5 has a bug, or two people press Book at the same moment, the database refuses anything that breaks the key rules.

4Things that happen without anyone pressing a button

WhatHow
A hold runs out after 10 minutes S8No timer needed. Each hold stores "held until 5:12". Any hold past its time counts as free. Nothing has to run.

My suggestion: one jobs script that runs every 15 minutes and does whatever is due. If the laptop was off at 6 pm, the next run catches up. For the prototype, Windows Task Scheduler can run it. On a real server, that server's scheduler does.

5Logging in: sessions or tokens?

Session (a coat check)

You hand over your coat and get a numbered ticket. The coat stays at the counter. The counter can cancel your ticket at any time.

In our system: after login, the server saves a session and gives the browser a random ticket in a cookie. To log someone out, the server deletes the session.

Token, or JWT (a signed pass)

You get a pass with a stamp. Anyone can check the stamp is real, and the counter keeps no list. But a pass can't easily be cancelled before it runs out.

In our system: a stolen token keeps working until it expires.

My suggestion: sessions.

  • When a password is reset at the counter, every old login should end straight away. With sessions, that's one delete.
  • There are only a few hundred users, so keeping a list of sessions costs nothing.
  • The cookie is HttpOnly, so code running in the page can't read it, and SameSite, so other websites can't use it.

6The tech choices left

Choice 1: TypeScript or plain JavaScript for React?

TypeScript. It has types like Java, so many mistakes show up in the editor instead of on a student's phone.

Choice 2: Sessions or tokens for logging in?

Sessions, as explained in part 5.

Choice 3: SQLAlchemy, or SQL written by hand?

The difference

SQLAlchemy writes everyday queries for us ("find Ana's bookings"). Writing SQL by hand gives full control but means much more code.

Both, each where it fits. SQLAlchemy for everyday queries. The key rules as real database rules (UNIQUE, CHECK, and "stock can't go below zero"). The booking transaction uses row locks, written so you can see the exact SQL. You'll understand every line, which is what interviews test.

Choice 4: How to run PostgreSQL on your laptop

You don't have PostgreSQL or Docker installed yet.

  • A. The PostgreSQL installer for Windows. One installer. It comes with pgAdmin, a tool for looking at your tables.
  • B. Docker Desktop, running PostgreSQL in a container. One command starts it, and it's easy to wipe and start fresh. It's also useful later for hosting, but it's one more thing to learn and set up now.

A for now. Fewer moving parts while we build. We can add Docker when we get to hosting.

Choice 5: What the tests run against

A real PostgreSQL test database, not SQLite. The most important rules (locks, database rules) only exist in PostgreSQL, so testing on anything else would skip them. One test will have two students race for the last slot at the same moment, and check that only one gets it.

Choice 6: How the code is organised

One repository with a backend/ folder and a frontend/ folder. The planning docs stay at the top. One place, one history, which is easy to show an interviewer.

8The order we'd build in

No dates. Each step ends with tests, a short quiz, and a DECISIONS.md entry. The parts marked you write are the core rules. You write them and I review, so you can explain every line.

  1. Set up: PostgreSQL running, the two folders, FastAPI says hello, React says hello.
  2. Tables: we design them together from CONSTRAINTS.md, placing each rule in a table, a database rule, or the code. you write the database rules
  3. Accounts and login: setup codes, the ID hash, passwords, sessions. you write the HMAC function and the setup-code check
  4. Items and stock: the screens to add items and update counts.
  5. Slots, holds and booking: the heart of the system. you write the booking rules and the transaction
  6. Packing and substitutes: the packing queue. you write the refill rule (U4)
  7. The counter: pickup, walk-ins, extras, fixing mistakes.
  8. Jobs: no-shows and deletions.
  9. Coordinator: settings, closed days, weekly totals.
