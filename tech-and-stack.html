1The big picture: three parts

Our system has three parts. They work a lot like the food bank itself.

Screens
React

Runs on Ana's phone or laptop, in the browser.

Like the front counter: what the student sees and taps.

⇄requests and answers
Server
FastAPI

Runs on one computer. Every rule lives here.

Like the volunteer who knows the rules and checks every request.

⇄SQL
Database
PostgreSQL

Stores everything, and refuses anything that breaks the key rules.

Like the shelves and the record book.

Example. Ana taps "Monday 3:40 pm". React sends a request: "hold this slot for me". FastAPI checks the rules: is booking open, and has it been 28 days? PostgreSQL saves the hold. The answer goes back, and Ana sees a 10-minute countdown.

Why not put everything on the phone?

Anything that runs on the student's phone can be changed by the student. Every browser has developer tools, and with them a curious student can switch off a check. If the 28-day check lived only in React, someone could remove it and book every week.

So the screens only show things and send requests. The server checks every rule again, and students can't touch the server.

Why a website and not a phone app?

  • It works on any phone, tablet or laptop, iPhone or Android, with nothing to install.
  • No app stores: no waiting for review, no developer fees, no updates for students to download.
  • Students with a full phone can still use it.
  • We don't lose anything we need. The main extra an app gives is notifications, and we don't send reminders anyway.

2The database: PostgreSQL

What it is

A database stores data in tables, like sheets in a spreadsheet. Each table has columns, and each line in it is called a row. PostgreSQL (people say "Postgres") is a free database used by many companies. It runs as its own program, and our server talks to it in SQL.

In our food bank

A small part of the varieties table might look like this:

idnamestock
7Chickpeas (canned)1
8Sunflower oil12
9Quick oats0
Why we need a real database, not a file

We could save everything in a file, like a spreadsheet. But at 5 pm on Sunday, many students book at the same moment. With a file, two saves at once can overwrite each other, and a booking quietly disappears. If the computer crashes in the middle of saving, the file can be left half-written. A database is built to handle both.

Why PostgreSQL: three things it gives us

a. Row locks: the last tin of chickpeas I4

There is one tin of chickpeas left. Ana and Ben both press Book at 5:00:01 pm, and both want it.

Without a lock

Ana's booking
Ben's booking
Reads chickpeas: 1 left
Reads chickpeas: 1 left
"1 is enough." Saves 0.
"1 is enough." Saves 0.
Both are promised chickpeas. There is one tin. One student goes home without it, and the count is wrong.

With a row lock

Ana's booking
Ben's booking
Locks the chickpeas row. Reads: 1 left
Wants the same row, so it waits
Saves 0, finishes, unlocks
still waiting
done
Now reads: 0 left
Ana gets the tin. Ben sees "Chickpeas just ran out" and picks something else.

The lock is two words added to a normal SQL line:

SELECT stock FROM varieties WHERE id = 7 FOR UPDATE;   -- "lock this row until I'm done"

Only that one row is locked. Someone booking rice and oil, with no chickpeas, doesn't wait at all.

b. Transactions: all or nothing

Ana's booking does several things: it takes her slot, takes each of her 13 items off the stock, and saves the booking. A transaction wraps them together so they either all happen or none do.

Example. The first 8 items go fine, but the 9th, quick oats, has 0 left. Without a transaction, Ana would have a slot and 8 items, and the stock count would be wrong. With a transaction, everything is undone as if she never pressed Book, and she's told the oats ran out.

c. Database rules: a safety net under our code

We write the rules in Python, but code can have bugs. So the most important rules are also written into the database. Then even buggy code can't break them: the database refuses the change.

-- Stock can never go below zero (I4)
stock integer NOT NULL CHECK (stock >= 0)

-- One upcoming booking per student (F2)
CREATE UNIQUE INDEX one_upcoming_booking
  ON bookings (student_id)
  WHERE status IN ('booked', 'packed');

The second rule says: among bookings that are still booked or packed, each student can appear only once. Old bookings that were picked up or cancelled don't count. It's called a partial unique index: "unique" because a student can't appear twice, "partial" because it only looks at some rows. you write these

A bonus: time zones. Newfoundland is half an hour off from most of Canada, which trips up a lot of software. PostgreSQL stores the exact moment of each time and can show it in Newfoundland time, half hour and summer time included. T1

What else we could use, and why not
OptionWhat it isWhy not for us
SQLiteA small database that lives in one file. It comes with Python, and it's inside most phone apps and browsers.Only one change can happen at a time in the whole database, and it can't lock a single row. At 5 pm everyone would queue behind one lock. It's great for an app on one device, not for a website many people use at once.
MySQLAnother popular free database, much like PostgreSQL.It would mostly work. But "one upcoming booking per student" (the partial index above) isn't possible in MySQL without a workaround.
MongoDBStores data as documents (like JSON) instead of tables. Good when every record has a different shape.Our data has a fixed shape and lots of links: a booking belongs to a student and has items, and each item has varieties. That's exactly what tables are for. MongoDB can do transactions now, but rules like "one upcoming booking per student" are simpler with tables.

In short: two students can want the last item at the same moment. PostgreSQL lets us lock just that row, undo a half-finished booking, and keep the key rules in the database itself.

3The server: FastAPI (Python)

What a server does

A server waits for requests, checks them, talks to the database, and sends an answer back. All our rules live here.

What FastAPI is

A Python package for building servers. You write a normal Python function and put a label on it saying which web address it answers.

In our food bank 
@app.get("/slots")
def list_slots(day: date):
    return get_free_slots(day)

When Ana's phone asks for /slots?day=2026-11-02, FastAPI:

  1. finds this function,
  2. checks that 2026-11-02 really is a date. If the phone sends banana, Ana gets an error and our function never runs,
  3. runs the function,
  4. turns the result into JSON (plain-text data the phone can read) and sends it back.
Why we use it
  • It checks incoming data for us, using Pydantic (part 4). That means fewer if-statements and fewer forgotten checks.
  • A free test page. Open /docs in the browser and you get a page listing every web address. You can fill in a form and try each one. We can test booking before a single screen exists.
  • Python. It's easy to read, and it's the main language for AI work, if we ever add the AI meal suggestions (on the "not in the prototype" list).
  • Small and clear. FastAPI only does the web part. The database part is SQLAlchemy and the data checks are Pydantic. Each piece is separate, so you can see how they fit and explain each one.

About the name: "Fast" is about speed, but speed isn't why we picked it. A few hundred students is tiny for any of these tools.

What else we could use, and why not
OptionWhat it isWhy not for us
FlaskAn older, simpler Python package for servers.It works, but it has no built-in data checking and no test page. We'd add extra packages for both, and FastAPI already has them.
DjangoA big Python package with everything built in: admin pages, accounts, its own database tool.Its accounts are built around usernames and emails. Ours are unusual: no names, no emails, a hashed ID number. We'd spend time working around Django instead of building. Its ready-made admin pages are a real plus that we give up.
Node.js with ExpressA server written in JavaScript.A fair choice, since the screens and the server would use one language. We picked Python because it's easier to read and it's the main language for AI.

In short: that one's yours. "Why FastAPI" is the blank line in DECISIONS.md. Pick the reasons above that matter most to you and write them in your own words.

4Checking the data: Pydantic

What it is

A package that describes what a request should look like, and checks every request against that before our code runs. It comes with FastAPI.

In our food bank 
class BookingRequest(BaseModel):
    hold_id: int
    items: list[int]          # the varieties Ana chose
    substitutes: list[int]    # in rank order

If the phone sends "hold_id": "abc", or leaves out items, FastAPI answers with an error (code 422) and our booking code never runs.

Shape versus rules

Pydantic checks the shape: "items is a list of numbers". Our own code checks the rules: "at most 13 items", "one of each item", "28 days have passed".

Why not put "at most 13" in Pydantic? Because 13 is a setting the coordinator can change. Pydantic's checks are fixed in the code, but settings live in the database.

A trap we'll handle. When Pydantic refuses something, FastAPI's error repeats the bad input back. If a student mistypes their ID number, that number could end up in an error message or a log. Rule P10 says it never can, so we'll change the error format and write a test for it.

What else we could use, and why not

There isn't a real choice here, because Pydantic comes with FastAPI. The other way is checking by hand with if-statements in every function, and it's easy to forget one.

In short: Pydantic stops badly shaped data at the door, so our rules only ever see clean data.

5Talking to the database: SQLAlchemy and Alembic

SQLAlchemy Choice 3

What it is

A package that lets Python talk to PostgreSQL. Each table becomes a Python class, and each row becomes a Python object.

In our food bank 
class Variety(Base):
    __tablename__ = "varieties"
    id:    Mapped[int] = mapped_column(primary_key=True)
    name:  Mapped[str]
    stock: Mapped[int]

Then "find Ana's bookings" looks like this in Python, and SQLAlchemy sends the SQL for us:

select(Booking).where(Booking.student_id == ana.id)     # what we write
SELECT * FROM bookings WHERE student_id = 42;           # what it sends
Why we use it
  • Less repeated code. Everyday "get this, save that" stays short.
  • Safe from SQL injection. If you build SQL by gluing text together, a user can type something that changes the query: 
    # Never do this
sql = "SELECT * FROM volunteers WHERE username = '" + name + "'"

# Someone types this as their username:   x' OR '1'='1
# and the query becomes:
SELECT * FROM volunteers WHERE username = 'x' OR '1'='1'   -- matches every volunteer
    SQLAlchemy always sends the values separately from the query, so whatever a user types is only ever treated as text.
  • We can still see and write the SQL when it matters. The booking's lock looks like this: 
    select(Variety).where(Variety.id == 7).with_for_update()
# sends: SELECT ... FROM varieties WHERE id = 7 FOR UPDATE
What else we could use, and why not
OptionWhat it isWhy not for us
Plain SQL only (psycopg)Write every query yourself as SQL text.Full control, but a lot more code, and the injection mistake above is easy to make. We'll still write the important SQL by hand where you should see it.
SQLModelMade by the person who made FastAPI, on top of SQLAlchemy. One class is both the table and the request shape.Neat for simple apps, but locks and partial indexes need SQLAlchemy underneath anyway, and there are fewer examples to learn from. Also, we want the table and the reply kept apart: the students table has the ID hash, and that must never be sent back in a reply. P4

Decided, Choice 3: both, each where it fits. SQLAlchemy for everyday queries. The key rules as real database rules (part 2c). The booking transaction written so you can see the exact SQL and the locks.

Alembic

What it is

A tool that keeps a numbered list of every change we make to the tables. It comes from the same people as SQLAlchemy.

In our food bank 
0001  create slots, varieties and bookings
0002  add "held until" to holds
0003  add the "one upcoming booking" rule

Running alembic upgrade head on any computer, whether your laptop, the test database or a real server later, builds exactly the same tables.

Why not change tables by hand?

You could add a column in pgAdmin with a few clicks. But then your laptop's database and the test database slowly become different, and nobody remembers what changed or when. With Alembic, every change is a file in git, with its own commit.

In short: SQLAlchemy is how Python talks to the database, safely. Alembic keeps every change to the tables written down, so every copy of the database matches.

6The screens: React, TypeScript and Vite

React

What it is

A JavaScript package for building screens out of small pieces called components. You describe what the screen should look like for the data you have now. When the data changes, React works out what's different and changes only that part of the screen.

In our food bank 
function SlotButton({ time, isFree }: { time: string; isFree: boolean }) {
  return <button disabled={!isFree}>{time}</button>;
}

The Book screen uses SlotButton 12 times, once per slot. When someone takes 3:40, React greys out just that one button.

Why we use it
  • Our screens change while you look at them. The 10-minute countdown ticks, "9 of 13 items chosen" goes up, and the packing queue gets a flag when a variety runs out. React is made for screens like this.
  • Pieces are reused. The Book screen and the Walk-in screen can share the same item picker.
  • It's the most used tool of its kind, so most questions already have an answer online.
What else we could use, and why not
OptionWhat it isWhy not for us
Plain HTML and JavaScriptWhat this page is made of.Fine for pages that don't change, like this one. On the Book screen you'd have to update every number, button and list by hand each time something changes. That gets messy fast.
Pages made by the server (Jinja, maybe with HTMX)FastAPI builds each page as HTML and sends the whole page.Honestly, this would work for us, and it's simpler because there's one program instead of two. But the countdown and the live item count are clumsier. With React, the server is a clean list of web addresses that we can test on their own.
Vue, Angular, SvelteOther tools like React.All would work. Vue is close to React. Angular is bigger, with more to learn. Svelte is smaller, with fewer examples online. React has the most help.

TypeScript Choice 1

What it is

JavaScript with types. You say what shape each thing has, and the editor checks that you use it correctly, while you type.

In our food bank 
type Slot = { id: number; startsAt: string; isFree: boolean };

showTime(slot.startAt);   // typo: red underline in the editor straight away

In plain JavaScript, slot.startAt just gives undefined, with no error. The screen shows a blank time, and you only find out by clicking through, or when a student tells you.

Why not plain JavaScript?

It needs less setup and less typing, but mistakes show up later on screen instead of right away in the editor.

Decided, Choice 1: TypeScript.

Vite

What it is

A tool that runs the React app while you work on it, and packs it into small files for the real website at the end.

Example: you save a change to SlotButton and the browser shows it straight away, without reloading the page.

What else we could use, and why not
OptionWhat it isWhy not for us

7Logging in: sessions Choice 2

Session: a coat check

You hand over your coat and get a numbered ticket. The coat stays at the counter. The counter can cancel your ticket at any time.

Token, or JWT: a stamped pass

You get a pass with a stamp. Anyone can check that the stamp is real, and the counter keeps no list. But a pass can't easily be cancelled before it runs out.

How a session works, step by step
1Ana types her ID number and password. The server checks them.
↓
2The server saves a session: a row saying "ticket 8f3k…9q belongs to this account". The ticket is a long random string that nobody can guess.
↓
3The server tells the browser to keep the ticket in a cookie, a small note the browser stores for one website.
↓
4From then on, the browser sends the cookie with every request by itself. The server looks up the ticket and knows it's Ana.
↓
5Logging out, or a password reset at the counter, deletes the row. The ticket stops working at once.
Two settings on the cookie
  • HttpOnly: code running on the page can't read the cookie. If a bad script ever got onto the page, it still couldn't steal Ana's ticket.
  • SameSite: the browser won't send the cookie when another website starts the request. So a trick page Ana visits can't cancel her booking behind her back.
Why not tokens (JWT)?

Example. Ana's flatmate knows her password, so she gets it reset at the counter.

  • With sessions: one delete, and the flatmate is logged out at once.
  • With JWT: the flatmate's token keeps working until it runs out. The fix is a list of cancelled tokens that the server checks on every request. That's a list of sessions again, with extra steps.

JWT is good when many separate servers must check logins without sharing a database. We have one server and one database.

What else we could use, and why not
OptionWhat it isWhy not for us
Log in with MUNStudents use their MUN login.Needs MUN's permission, which we don't have. It could come later if MUN gets involved.
Login services (Auth0, Firebase Auth)Another company runs the logins for you.Student data would sit with another company, and these services are built around email addresses. We store no emails. P3

Decided, Choice 2: sessions, with an HttpOnly, SameSite cookie.

8Keeping secrets: argon2 and HMAC

Passwords: argon2 P8

What a hash is

A hash turns a password into a scramble that can't be turned back. We store only the scramble. To check a login, we scramble what Ana typed and compare.

Why: if the database ever leaks, the thief gets scrambles, not passwords. That matters because many people use the same password everywhere.

Why argon2, and not a normal hash like SHA-256?

SHA-256 is built to be fast. A gaming graphics card can try billions of SHA-256 guesses a second. argon2 is slow on purpose and needs a lot of memory for every guess. For Ana, logging in takes a fraction of a second. For a thief trying millions of guesses, it takes far, far longer.

Salt: argon2 also mixes a random "salt" into each password before scrambling. Two students who both pick Pasta123 get different scrambles, so cracking one doesn't crack the other.

What else we could use

bcrypt is older and still fine. argon2 is newer, and it's the first choice in OWASP's guide, a well-known guide to web security.

ID numbers: HMAC P2 you write this

The problem

When Ana logs in or shows her card, we must find her account from her ID number, without ever storing the number.

Why not a plain hash?

There are only a billion 9-digit numbers. A laptop can hash all of them in minutes and make a list: scramble → number. With that list, any scramble turns straight back into the ID number. A plain hash barely hides it.

What HMAC does

HMAC is a hash mixed with a secret key. Without the key, nobody can make that list. The key is kept outside the database, so stealing the database alone isn't enough. P11

ID number 202312345+ secret key→ HMAC→ a91f…→ find the account with a91f…
Why not argon2 for the ID too?

argon2 adds a random salt, so the same ID would give a different scramble every time. That's fine for passwords, because we already know whose account to check. But for the ID, we have to search: "which account has this scramble?" That only works if the same ID always gives the same scramble, which is what HMAC does.

Why not encryption?

Encryption is made to be undone with the key. We never need the number back, only to check "is this the same card?". So we don't keep a way back.

In short: passwords get a slow, salted hash (argon2). ID numbers get a keyed hash (HMAC), so we can still find the account but can't turn it back into the number.

9Testing: pytest, on a real PostgreSQL Choice 5

What it is

pytest runs test functions. Each one sets up a situation and checks the result. If anything breaks later, the test fails and tells us.

In our food bank 
def test_too_soon_after_last_pickup():
    ana = make_student(last_pickup=date(2026, 10, 1))    # Thursday 1 Oct
    with pytest.raises(TooSoon):
        book(ana, slot_on(date(2026, 10, 26)))           # Monday 26 Oct: only 25 days

def test_allowed_after_28_days():
    ana = make_student(last_pickup=date(2026, 10, 1))
    book(ana, slot_on(date(2026, 10, 29)))               # Thursday 29 Oct: 28 days, fine
Why a real PostgreSQL, not SQLite?

Our most important test: two students try to book the last slot at the same moment, and exactly one may win. That test checks the row lock and the database rules from part 2. SQLite has neither, so the test would pass without testing anything real.

The tests use their own test database, separate from the one you work with, so they can't mess up your data.

What else we could use, and why not
OptionWhat it isWhy not for us
unittestThe test tool built into Python.It works, but needs more typing: classes and self.assertEqual(a, b) instead of a plain assert a == b.
Testing on SQLiteA faster, throwaway database for tests.It skips exactly the rules that matter most: locks and database rules.
A pretend databaseFake the database inside the test.Same problem. The real database rules never run.

Decided, Choice 5: pytest against a real PostgreSQL test database.

10Running PostgreSQL on your laptop Choice 4

Your laptop has Python 3.11 and Node 24, but not PostgreSQL yet. There are two ways to get it.

A. The Windows installer

One installer. PostgreSQL then runs in the background whenever the laptop is on.

It comes with pgAdmin, a window for looking at your tables and trying SQL.

B. Docker

Docker runs programs inside containers: sealed boxes with everything the program needs already set up. One command starts PostgreSQL in a box. Delete the box and start fresh any time.

The same box runs the same way on any computer, which helps later when we put the system online.

Why A for now

On Windows 11 Home, Docker needs WSL 2 (a small Linux inside Windows) set up first. That's one more thing to learn, and to fix if it goes wrong, on top of everything else that's new. We can add Docker when we get to putting the system online.

Decided, Choice 4: A, the Windows installer.

11One repository Choice 6

All the code, in a backend/ folder and a frontend/ folder, goes in the repository that's already on GitHub, next to the planning docs.

Example. We add "held until" to slot holds. The table change, the server change and the countdown on screen all go into one commit: "Add 10-minute slot holds". One change, one story.

Why not two repositories? The same change would be two commits in two places. They can get out of step, with the screens expecting something the server doesn't have yet. And anyone reading your GitHub would see half the story in each.

Decided, Choice 6: one repository.

12Things that happen by themselves

WhatHow
A hold runs out after 10 minutes S8Nothing needs to run. Each hold stores "held until 5:12 pm". Any hold past its time counts as free.
Booking opens at 5 pm and closes at 12 pm S5Nothing needs to run. The server compares the time now with that day's open and close times.
Bookings not picked up become no-shows at 6 pm B3A small jobs script.
Delete booking details after 90 days, and accounts after a year P7 P13The same jobs script.

The jobs script runs every 15 minutes and does whatever is due. On your laptop, Windows Task Scheduler can run it. On a real server, that server's scheduler does.

Why it's built this way
  • Why not a timer for every hold? 50 students holding slots would mean 50 timers. If the server restarts, the timers are lost and those slots stay stuck. A stored "held until 5:12 pm" can't be lost.
  • Why every 15 minutes, not exactly at 6 pm? If the computer is off at 6 pm, a 6 pm job is simply missed. A job every 15 minutes catches up on its next run.
  • Why not a job queue (like Celery with Redis)? Those are extra programs that run all the time, made for systems with thousands of background tasks. We have one small script.

13Putting it together: one booking, start to finish

Ana presses Book on Sunday at 5:08 pm. Here is every stop on the way, and what each one checks.

1Ana's phone (React) sends POST /bookings with her held slot, items and substitutes. Her login cookie goes with it automatically.
↓
2FastAPI finds the Python function for POST /bookings.
↓
3Login check: the cookie's ticket says this is Ana's account. If she isn't logged in, she sees "please log in". P6
↓
4Pydantic checks the shape: items and substitutes are lists of numbers. If something's wrong, she gets an error, and the error never repeats her ID number back. P10
↓
5Booking rules (plain Python): is booking open? 28 days? no other booking? didn't cancel for this day? is the hold still hers? at most 13 items, one of each? S5 F1 F2 S6 S8 I3 you write this
↓
6SQLAlchemy → PostgreSQL, one transaction: lock the slot, take each item off the stock (never below zero), save the booking. If our code missed anything, the database's own rules stop it. S2 I4 B4 you write this
↓
7Back to Ana: "Booked. Your booking code is K3P."

Why check the rules twice, in step 5 and again in step 6? Step 5 gives Ana a clear message, like "28 days haven't passed yet". Step 6 is the safety net: even if step 5 has a bug, or two people press Book at the same moment, the database refuses anything that breaks the key rules.

The rules live in services/, apart from the web addresses in routes/. That way, a test can check the booking rules directly, without going through the web part at all.

The order, with no dates. Each step ends with tests, a short quiz, and a DECISIONS.md entry. The parts marked you write are the core rules. You write them and I review, so you can explain every line.

  1. Set up: PostgreSQL running, the two folders, FastAPI says hello, React says hello.
  2. Tables: we design them together from CONSTRAINTS.md, placing each rule in a table, a database rule, or the code. you write the database rules
  3. Accounts and login: setup codes, the ID hash, passwords, sessions. you write the HMAC function and the setup-code check
  4. Items and stock: the screens to add items and update counts.
  5. Slots, holds and booking: the heart of the system. you write the booking rules and the transaction
  6. Packing and substitutes: the packing queue. you write the refill rule (U4)
  7. The counter: pickup, walk-ins, extras, fixing mistakes.
  8. Jobs: no-shows and deletions.
  9. Coordinator: settings, closed days, weekly totals.
