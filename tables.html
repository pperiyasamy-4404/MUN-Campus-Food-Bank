The tables, explained simply

This page is the plan for the database: which tables there are, what goes in each one, and where every rule from CONSTRAINTS.md is kept. Nothing on it is built yet.

Nine choices are marked like this Choice A and listed again in part 11. All nine were agreed on 3 Nov 2026, as suggested.

Built the same evening: the tables and their rules are in backend/app/models/, and every rule has a test in backend/tests/test_database_rules.py that tries to break it. Part 12 lists what exists now.

A few words used on this page

Table, row, column
A table is like one sheet in a spreadsheet. Each column holds one kind of fact (like stock), and each row is one thing (like one variety of oats).
Primary key
The column that names each row, so no two rows are the same. Usually a number called id: 1, 2, 3…
Link (foreign key)
A column that points to a row in another table. bookings.student_id = 41 means "this booking belongs to student 41". The database refuses a link to a row that doesn't exist.
Empty (NULL)
A column with nothing in it. In the examples below it's shown as —.
Database rule (constraint)
A rule written into the table itself. The database refuses any change that breaks it.
CHECK
A database rule about one row, like "stock is 0 or more".
UNIQUE
A database rule that no two rows can have the same value, like "no two students have the same ID hash".
Partial unique index
UNIQUE, but only among some rows, like "among bookings that are still booked or packed, each student appears once".
Migration
A numbered file, made by Alembic, that creates or changes tables. Running it builds the same tables on any computer.

1The whole map

Here are the 19 tables in four groups. An arrow means "each row here points to one row there". For example, each booking points to one student, and each slot points to one pickup day.

A booking also stores its pickup day, as well as its slot. That arrow is left off the map to keep it readable. Part 6 explains why it's there.

2Three places a rule can live

Every rule in CONSTRAINTS.md ends up in one or more of these places.

table shape

Which columns exist. If there's no column for something, it can't be stored.

Example. students has no name column, so no code can ever save a student's name. P3

database rule

Written into the table. The database refuses any change that breaks it, even from buggy code, even when two people press Book at the same moment.

Example. stock can't go below 0. I4

code

The rules in Python. They give clear messages, and they can use dates, settings and many rows at once.

Example. The 28-day gap needs the last pickup date, today's date in Newfoundland, and the pickup gap setting. F1

What a database rule can see

Not much, and that's on purpose. A CHECK sees one row at a time. A UNIQUE rule compares a column across all rows. A link checks that the row it points to exists. That's all.

So "at most 13 items per booking" can't be a database rule. It means counting rows in another table and comparing with a setting. That goes in the code.

Why not put more in the database?

PostgreSQL can run whole programs inside the database, called triggers. But then rules hide in the database where nobody looks, they're harder to read and test, and their error messages are poor.

Why not put everything in the code?

Code can have bugs, and two requests can arrive at the same moment. The rules that must never break need a guard that works even then.

Our rule of thumb: the code checks everything first and explains the problem to the student. The database guards the few rules that must never break, as a safety net under the code.

booked_count is like stock, turned upside down. Stock counts what's left and can't go below 0. booked_count counts what's taken and can't go above capacity. Booking adds 1, and cancelling takes 1 away. S2

Example. Slot 301 has 1 booking. If two students press Book on it at the same moment, the database rule lets only one of them in. Database rules: capacity is at least 1, booked_count stays between 0 and capacity, and a day can't have two slots that start at the same time. S2

6Holds and bookings

holds: a slot, kept for 10 minutes

student_idslot_idheld_until

Student 41 picked the 3:40 slot at 5:02 pm, so it's theirs until 5:12. A hold past its time counts as free, so nothing has to delete it on time (tech page, part 12). S8

student_id is the primary key, so a student can have at most one row here, which means one hold at a time. Picking another slot replaces the row. S8

Holds aren't in booked_count. Before giving a hold, the code locks the slot and checks that there's room for it: the bookings, plus other students' holds that haven't run out. If that code had a bug, the worst case is that a student loses their hold when they press Book. The slot is still never overbooked, because the database rule on booked_count catches it.

Database rule: one hold per student, from the primary key.

Holds are in their own small table. Choice C

Why the booking stores its day, when the slot already knows it: the rule "a student who cancels can't book again for that same day" S6 needs the day in the booking row, so a UNIQUE rule can see it. Database rules:

  • The status is one of the five. B1
  • One upcoming booking per student: among bookings that are booked or packed, each student appears once. This also makes a double click on Book harmless, because the second booking is refused. F2 B4
  • One booking per student per pickup day, of any status, so cancelling and booking again can't be used to change items. S6 I7
  • A booking code is unique within its day. P4
  • The booking's day matches its slot's day.
  • The status always matches the times saved with it. A picked-up booking has a pickup time and the volunteer who clicked B3. A cancelled one has a time and a reason. A no-show has a time.

"One booking per student per pickup day" is a database rule, not only a code check. Choice F

What pressing Book changes, in one transaction

Here's student 41 pressing Book at 5:08 pm. If any step is refused, everything is undone, as if they never pressed it.

1Lock slot 302. Check the hold is still theirs and hasn't run out.
↓
2Delete the hold.
↓
3Slot 302: booked_count 0 → 1. The database checks it's still within capacity.
↓
4Save booking 88. The database checks: one upcoming booking, one booking that day, the code is unique, and the day matches the slot.
↓
5For each item, in variety order: save it and take 1 off its stock. The database checks that stock stays 0 or more.
↓
6Save the substitutes.
↓
Booked. Code K3P.

Why "in variety order" in step 5: if one booking takes oats then chicken while another takes chicken then oats, each can end up waiting for the row the other has locked, forever. That's called a deadlock. If every booking takes them in the same order (lowest id first), it can't happen. This is the same idea as the 25 Oct decision about lock order. You'll write this transaction in step 5.

7Times, numbers and words

Three kinds of time T1
KindExampleWhy
A moment: timestamptzbooked_at, held_until, booking_opens_atSaved as one exact moment (in UTC) and shown in Newfoundland time. Summer time and the half hour are handled for us.
A calendar date: datepickup_date, last_pickup_onThe 28-day rule counts calendar days in Newfoundland F1, so a pickup at 5 pm and a slot at 3:30 pm four weeks later are 28 days apart.
A clock time: timeThe settings: 17:00, 12:00, 18:00Means "this time on a Newfoundland clock". It's turned into a moment when a pickup day is made, so each day gets the right summer or winter time.

Why not save plain clock times everywhere? On 1 November the clocks went back, and 1:30 am happened twice. A plain clock time can't say which one it means. A moment can.

ids are plain numbers

The database hands them out: 1, 2, 3. Why not long random ids (UUIDs)? Plain numbers are easier to read in pgAdmin while we learn. Nothing secret depends on them, because the server checks on every request that the booking belongs to whoever is asking. Students see the booking code, never the id.

Statuses are text with a CHECK

Like status IN ('booked', 'packed', …). Why not PostgreSQL's own list type (an enum)? Adding a value to an enum has some catches, and taking one away isn't possible at all. Changing a CHECK is one line in a migration.

Names

Lowercase with underscores (booking_items). Tables are plural, and a link column is the table's name in the singular plus _id (student_id).

11The nine choices

All nine agreed on 3 Nov 2026, as suggested. Choice I changed on the same day: Claude writes the rules as well as the tests (see the note in that card).

A. Students and staff in two tables, not one "accounts" table

Why: they have different columns. A student has an id_hash, and staff have a username and a role. A booking can only point to a student, so it can never point to a volunteer by mistake. A list of volunteers can never include an id_hash P4. And deleting accounts after a year only ever touches students.

Why not one table: every row would have empty columns, and we'd need extra rules like "a student has an id_hash and no username".

The cost: sessions and setup codes need two link columns, with the rule "exactly one is filled".

B. Slot capacity as a count on the slot, guarded by a database rule

Why: the rule sits on the row the booking locks anyway, so the database itself refuses a second booking in a one-student slot. It works the same way as stock.

Why not count the bookings each time: it works in code, but a database rule can't count rows, so there'd be no safety net. Why not a trigger: it would be hidden code inside the database.

The cost: the count must change in the same transaction as the booking: plus 1 at Book, minus 1 at cancel. In step 5, a test will check that the count always matches the bookings.

C. Holds in their own small table, one row per student

Why: a hold has no items, no code and no status. Making student_id the primary key gives "one hold at a time" S8 for free. And bookings only ever holds real bookings, which keeps the totals simple.

Why not a "held" status on bookings: half-made bookings would sit in the bookings table, and every list and every total would have to skip them.

D. Each pickup day is its own row, with its own times

Why: moving one day's times S9 or closing a day S7 changes one row. Changing the settings never moves a day students can already see.

Why not work the times out from the settings each time: S9 would need a separate list of exceptions, and changing a setting would silently move days that are already open.

E. Dietary tags in their own table

Why: the coordinator can add a tag, like vegan or dairy-free, without a code change.

Why not four yes/no columns on varieties: simpler at first, but every new tag would need a code change and a migration.

F. "One booking per student per pickup day" as a database rule

Why: rule S6 exists to stop "cancel and book again to change my items" I7. With a database rule, even buggy code can't let that happen.

The cost: the booking stores its day as well as its slot, and a link on the pair (slot, day) keeps them matching.

Why not only a code check: the code checks it anyway, to give a clear message. This is the safety net under it.

G. The activity log is deleted after the retention period, like booking details

Why: log rows say which student was served on which day, which is a booking detail P7. Keeping them longer would keep a history we promised to delete.

The cost: after 90 days, we can't see who fixed a no-show. Fixes should happen before the next booking window anyway B6.

H. Build now the tables that steps 3 to 5 use, and add the others in their own steps

Why: we'll understand packing and the counter better once we're writing them. Adding a table later is a normal, small Alembic step, and each later commit tells one story, like "Add walk-ins".

Why not every table now: we'd be guessing at details, and we'd probably change them later anyway.

I. Every rule has a test that tries to break it

Why: the tests stay in the repository as proof that the rules work, and anyone can read a rule next to the test that breaks it. Each test checks the name of the rule that refused, so it fails for the right reason only.

Changed on 3 Nov: the plan was that you write the rules until my tests pass. You asked Claude to write the rules too, and to learn how they work afterwards. To be sure the tests really test something, two deliberately wrong tests were run once (wrong rule name, and no refusal at all). Both failed, as they should.
