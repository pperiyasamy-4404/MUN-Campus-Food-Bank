Accounts and logging in

Students, volunteers and the coordinator can now have accounts and log in. A volunteer checks a MUN card at the counter and gives a one-time setup code. The student chooses their own password on their own phone. This page explains how every piece works, and why it's built that way.

1Three kinds of people, three ways in

WhoLogs in withTheir account is made byStays logged in
StudentID number from their MUN card + passwordA volunteer at the counter, after checking the card R130 days after their last visit
VolunteerUsername (like "Sam") + passwordThe coordinator R312 hours after logging in
CoordinatorUsername + passwordA setup script, run once on the server12 hours after logging in

Everyone chooses their own password with a setup code: a one-time code like K7QM-4TXP. Nobody else ever sees the password, not the volunteer, not the coordinator.

Why make accounts at the counter, not with an online sign-up? With a sign-up page, anyone could register someone else's ID number before its owner does, made-up numbers could get accounts, and the page would have to say "this number already has an account", which tells a stranger that person uses the food bank. At the counter a volunteer has the real MUN card in their hand.

Why not email a reset link? We don't store email addresses P3. A forgotten password is reset the same way: a new code from the counter.

2Setup codes

A setup code is 8 characters from 31 letters and digits, shown as two groups of four: K7QM-4TXP. The letters O, I and L and the digits 0 and 1 are left out, so nobody misreads 0 as O from a slip of paper.

  • It works once. Using it deletes it.
  • It runs out after the setup code lifetime: 7 days in the sample settings.
  • Each account has at most one. A new code replaces the old one.
  • The old password keeps working until the new code is used. So a code given by mistake locks nobody out.
  • Using a code logs the account out everywhere else. If a flatmate was logged in on the student's laptop, they're out straight away.
  • Small letters and spaces are fine. k7qm 4txp is the same code.

How hard is it to guess one? 318 is about 850 billion codes. With 5 tries every 15 minutes (section 6), that's 3,360 tries in 7 days: a chance of about 1 in 250 million.

Why not a 6-digit number, like a bank's text message? Only a million of them. That's still fine with slow tries, but 8 characters costs nothing extra and leaves a big safety margin if the try limit is ever loosened.

3What the database keeps, and what it never keeps

Three different ways of "scrambling" text are used, each for its own reason. A hash turns text into a fixed-length string, and it can't be turned back.

What a person types or holdsWhat the database keepsHowWhy that way
ID number 2023987659f2c… (64 characters)Keyed hash (HMAC-SHA256), with the secret key from backend/.envThere are only a billion 9-digit numbers. Without a key, anyone could hash them all and look the answer up. The key isn't in the database, so a stolen copy is useless P2
Setup code K7QM-4TXP51ab…Keyed hashSomeone reading the database can't use a code before the student does
Password$argon2id$v=19$m=65536,t=3,p=4$…argon2: slow on purpose, with a random saltEach guess costs about a tenth of a second and 64 MB of memory, so trying millions is hopeless P8
Login ticket in the cookiee3b0…Plain SHA-256A ticket is 256 random bits. Nobody can list every possible ticket the way they could list ID numbers, so no key is needed

The database itself refuses anything else. A password hash must start with $argon2id$, and the ID hash and code hash must be exactly 64 characters of 0–9 and a–f. If some code had a bug and tried to save the real password or the 9 digits, PostgreSQL would refuse it. These rules came in with migration 8be36cf65217.

Why argon2 and not bcrypt? argon2 is OWASP's first choice today. Its need for memory makes guessing on graphics cards expensive. bcrypt also quietly ignores everything after 72 bytes.

Why not argon2 for the ID number too? We have to find the student from the number they type. A keyed hash always gives the same answer for the same number, so it can be looked up. argon2 adds a random salt, so the same number gives a different hash every time, and there would be nothing to look up.

4Logging in: what gets checked

When a student presses Log in, log_in_student in app/services/accounts.py does this:

  1. Tidy the number: 2023 98765 becomes 202398765. Anything that isn't 9 digits is refused with "Enter the 9 digits on your MUN card."
  2. Work out its keyed hash, and find the student with that hash.
  3. Check the wrong-tries count (section 6). Too many? Stop here with "Try again in 14 minutes."
  4. Check the password against the argon2 hash.
  5. Wrong? Save one wrong try and say "That ID number and password don't match."
  6. Right? Forget earlier wrong tries, make a login ticket, and send it back in a cookie.

The same words for every kind of wrong

No account for that number, an account with no password yet, or the wrong password: the answer is always the same sentence. Even the time it takes is the same. With no account, the password is still checked, against a made-up argon2 hash, so a wrong number takes as long as a wrong password.

Why: otherwise anyone could type ID numbers and learn which ones have accounts, which means learning who uses the food bank.

5The login ticket and its cookie

After a right password, the server makes a ticket: 43 random characters. The browser keeps it in a cookie and sends it back with every request. The server keeps only a hash of it, in the sessions table, with the time it runs out.

Set-Cookie: session=Xq3…(43 characters); Max-Age=2592000; HttpOnly; Secure; SameSite=strict
                                         30 days         ↑ page code can't read it
                                                          ↑ only over https
                                                                  ↑ never sent from another website
Cookie settingWhat it stops
HttpOnlyCode running on the page can't read the ticket, so a bug that let someone add code to the page still couldn't steal it.
SecureThe cookie is only sent over https, never as plain text on café Wi-Fi. Browsers count localhost as safe, so it works while we build.
SameSite=strictAnother website can't make the student's browser send a request with their login, like "cancel my booking".

How long a login lasts (your choice, 5 November)

Students: 30 days after their last visit.

Places go fast at 5 pm, so nobody should have to find their password on booking night. Each visit moves the 30 days on, but at most once a day, so not every page load writes to the database.

Staff: 12 hours after logging in.

The counter laptop is shared. A staff login never lasts overnight, however busy the shift. Visits don't move it on.

Why a ticket in the database and not a token (JWT)? This was decided on 1 November: a password reset at the counter has to log the old browser out at once. With tickets that's one deleted row. A JWT keeps working until it runs out.

6Wrong tries: slowed down, never locked

Rule P9: wrong passwords are limited per ID number, and the account is never locked. After 5 wrong tries in 15 minutes, the answer is "Too many wrong tries. Try again in 15 minutes." and the password isn't even checked. Once the oldest of those 5 tries is 15 minutes old, one more try is allowed.

  • Wrong setup codes count too, or a guesser would try codes instead.
  • Numbers with no account are slowed down too. Otherwise "wait" would mean "this number has an account".
  • A right password forgets the earlier slips.

The "trusted device" cookie

There's a catch. Anyone who knows a student's ID number could type 5 wrong passwords every 15 minutes, and keep the real student waiting on booking night. So a browser that has logged in to an account before gets a second cookie, called device. It says "this browser has logged in here before". Its wrong tries are counted on their own.

The cookie is signed with the secret key, so nobody can make one for someone else's account. It still allows only 5 tries per 15 minutes, on that phone. It lasts a year and doesn't log anyone in. This idea comes from OWASP, which calls it a "device cookie".

Ten tries at the same moment

Without care, 10 wrong tries sent at once would each count 0 earlier tries, and all 10 would be checked. So before counting, the server takes a lock on that count in PostgreSQL (pg_advisory_xact_lock). The other tries wait their turn, and the lock is let go when the answer is saved. A test really sends 10 tries on 10 connections, and checks that exactly 5 are checked and 5 are told to wait.

The check is a dependency, like db and now on the database page. A route just says who it needs:

@router.get("/volunteers")
def list_volunteers(coordinator: CurrentCoordinator, db: DB) -> list[VolunteerOut]:

CurrentCoordinator reads the cookie, finds the login, and checks the role, all before the route's own code starts. Nobody logged in gets 401 "Please log in.". A volunteer gets 403 "Only a coordinator can do this.".

Why a dependency and not an "if" inside each route? A route can't forget it. If the type says CurrentCoordinator, the check runs. The pages also hide what you can't use, but that's only for looks: the server checks every request on its own.

8Keeping the ID number out of everything

Rule P10: the ID number never appears in web addresses, logs or error messages. Five things make sure of that:

  1. Only in the body of a POST. Never /api/student?id=202398765: addresses end up in browser history and server logs. A test checks that no address takes an ID number, password or code in the web address.
  2. FastAPI's own error answer is replaced. It repeats what was typed. A mistyped number would come straight back: 
    FastAPI's own:  {"loc": ["body","id_number"], "msg": "...", "input": "20239876"}
Ours:           {"loc": ["body","id_number"], "msg": "Enter the 9 digits on your MUN card."}
  3. Secrets are SecretStr. If one is ever printed by mistake, it shows as **********.
  4. Database errors hide their values (hide_parameters=True), so an error that gets logged can't show a hash.
  5. No answer is stored by the browser (Cache-Control: no-store). A setup code on screen doesn't come back when someone presses Back.

Then one test checks it all. It takes one ID number through everything that touches it: the counter, a mistyped number, a wrong code, a short password, setup, a wrong password, logging in. Then it searches every answer, every log line (each SQL statement included) and every row of every table for those 9 digits.

Does the test really catch a leak? We checked: with FastAPI's own error answer put back, the test fails with "the ID number is in the answers". With ours, it passes.

Small things that matter at a real counter

  • The volunteer types the card number twice. A typo would make an account for someone else's number, and the student's code wouldn't work with their real one.
  • The number leaves the screen as soon as the code is given. "Done, clear the screen" removes the code too, before the next person steps up.
  • New passwords are typed twice. A typo would mean another trip to the counter. A "Show the password" box helps on a phone.
  • "Please don't use your MUN password" is on the setup page P8.
  • No logging in on top of someone else. If a volunteer is logged in on the counter laptop, the student pages say "You're logged in" and ask students to use their own phone. Otherwise a student would replace the volunteer's login, and stay logged in on a shared laptop for 30 days.
  • Phones: boxes are big enough to tap, and text is at least 16 px, so phones don't zoom in. The ID number box opens the number keypad.

Why React Router? It's the standard way to do this in React. Many screens are coming (booking, packing queue, counter, coordinator), and each needs its own address. Why not write our own? 30 lines would cover today, but Back-button handling, links and "page not found" add up quickly.

12Three questions, answered

1. Can the coordinator give students setup codes? Yes. The rules list it for volunteers, but a coordinator helping at the counter shouldn't need a second account. The log says who gave each code either way.

2. A volunteer who comes back. The coordinator presses Switch back on. They keep the same account and username, so the log keeps everything they did under one name. Their old password stops working, and they choose a new one with the setup code that appears. They may have been away for months, and the old password could have been shared or forgotten since. A code handed over in person also shows it really is them.

3. A stranger guessing can delay a reset on a new phone. Left as it is for now, and listed under "Known issues" in CONSTRAINTS.md. If someone keeps guessing a student's password, the student's usual phone still gets in. A new phone has no device cookie, so it shares the stranger's count, and may wait up to 15 minutes to use a new setup code. It needs a stranger who knows the ID number and keeps guessing.

Left for the jobs script (step 8): deleting old wrong tries, logins that have run out, and unused setup codes. Until then they just sit in their tables, ignored.

13How to run it and try it

Each server needs its own terminal. The folder name has a space, so keep the quotes.

# Terminal 1: the server
cd "D:\MUN Project\backend"
.venv\Scripts\python -m uvicorn app.main:app --reload

# Terminal 2: the pages
cd "D:\MUN Project\frontend"
npm run dev

Then make your own coordinator account, in a third terminal:

cd "D:\MUN Project\backend"
.venv\Scripts\python -m app.first_coordinator YourName

Open http://localhost:5173/staff/setup, type the username and the code it printed, and choose a password. From there:

  1. Counter: type a made-up 9-digit number twice, and get a code.
  2. Open a private window (it has its own cookies, like a student's phone), go to "Set up your account", and use that number and code.
  3. Volunteers: add one, then set them up in another private window.

Use made-up numbers only. Real ones wait until the Campus Food Bank agrees to anything live.
