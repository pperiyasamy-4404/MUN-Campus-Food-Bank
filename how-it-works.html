Campus Food Bank Booking System

How it works, step by step

This page explains everything we have decided so far, from the beginning. It follows a student from getting an account to picking up their food, and then shows what volunteers and the coordinator do.

Codes like F1 or P3 are the rule numbers in CONSTRAINTS.md. Anything we haven't decided yet is marked Not decided yet. Problems we accept for now are marked Known issue.

1What we are building

MUN's Campus Food Bank gives free food to students. We are building a website where a student can:

  • book a 10-minute time to pick up food (a slot),
  • choose their food from what is in stock, before they come,
  • and collect a bag that volunteers have already packed.

At the same time, the system has to keep some promises:

  • Fair: one pickup every 30 days per person. F1
  • Private: no names, emails, phone numbers or MCP numbers, anywhere. P3
  • Honest about stock: never promise food that isn't there. I4
  • Within limits: no slot ever gets more students than it can take. S2

This is a prototype with sample data. The real rules will be agreed with the Campus Food Bank later. Every number that might change (30 days, 13 items, 5 pm…) is a setting the coordinator can change without touching the code. So switching to the real rules means changing settings and the item list, not rewriting the code.

Each booking is for one person. Families aren't in the prototype.

2The three kinds of users

Student

  • Has an account, made at the counter R1
  • Books a slot, then chooses items
  • Ranks up to 5 substitutes
  • Can cancel until 12 pm on the pickup day
  • Picks up the bag

Volunteer

  • Sees the packing queue for their shift R2
  • Packs bags, applies substitutes, and writes swaps on a sticky note
  • Hands out booked bags after checking the MUN card, and marks them picked up
  • Serves walk-ins in their own line
  • Records extras given out
  • Updates stock counts before each booking window
  • Creates student accounts and setup codes

Coordinator

  • Manages items and stock R3
  • Changes the settings
  • Closes days (holiday, snow, Christmas)
  • Creates volunteer accounts, with a setup code
  • Sees weekly totals only, never who picked up

3The big picture

Everyone uses the same website. Behind it there is a server that checks the rules and a database that stores the data.

  • Website (React): the screens. It shows things and sends what the person clicked to the server. It doesn't decide anything, because anyone can change what runs in their own browser.
  • Server (FastAPI): every request goes here. It checks the rules (is booking open? has it been 30 days?) and only then changes the database.
  • Database (PostgreSQL): keeps all the data. The most important rules are also built into the database itself: slot capacity, stock never below zero, and one upcoming booking per person. These hold even if the server code has a bug.
  • Secret key: used to scramble ID numbers (next section). It's kept outside the database, so a stolen copy of the database is useless without it.

Why PostgreSQL? The booking rules need real transactions and row locks (explained in section 9 and section 17). SQLite can't lock single rows.

4Keeping students private

One person, one identity: the MUN ID number. P1 Only this one kind of ID is accepted, so nobody can have two identities and get food twice. We don't use the MCP (health card) number: international and out-of-province students don't have one, and it's too sensitive to keep.

The ID number itself is never saved. P2 We save a keyed hash of it instead.

What is a hash?

A hash turns any text into a fixed jumble of letters and numbers. The same input always gives the same jumble, but you can't turn the jumble back into the input. So the system can check "is this the same person as last time?" without keeping the number.

When a student types their ID number, the server makes the keyed hash again and looks for it in the database. The number itself is thrown away straight after.

Why not a plain hash? MUN ID numbers have 9 digits, so there are only about a billion of them. A computer can hash all of them very quickly and build a lookup table: jumble → number. With a keyed hash (HMAC), the secret key is mixed in. Without the key, nobody can build that table.

What we save

  • The keyed hash of the ID number
  • A hash of the password
  • Bookings: day, slot, items, substitutes, status (for 90 days)
  • Totals, like pickups per week and items given out

What we never save P3

  • The ID number itself
  • Names
  • Emails or phone numbers
  • MCP numbers
  • Passwords as plain text
  • …and none of these in logs either

Volunteers never see the ID number or its hash on screen. P4 They see a booking code and the items. They do read the number off the card to type it in, but the screen never shows it back.

Other privacy and safety rules

  • The ID number never appears in web addresses, logs or error messages. A test checks this. P10 (FastAPI normally repeats bad input back in its error messages, so we have to switch that off.)
  • The secret key is backed up somewhere safe, outside the database. If it were lost, no card could be matched to its account again. P11
  • The coordinator sees totals by week, and any number under 5 shows as "fewer than 5", so nobody can work out who came on a quiet day. P12
  • Accounts with no pickup for a year are deleted. P13
  • Every volunteer has their own login, and the system logs who created accounts, issued setup codes, recorded walk-ins and marked pickups. R4

5Step 1: Getting an account

Why accounts? If an ID number alone were enough, anyone who knew a student's number could book in their name and block them, fill slots with made-up numbers, or find out whether they use the food bank. A password stops that.

Why at the counter, and not a sign-up page? Online, someone could sign up with another person's number before they do, and made-up numbers could get accounts. The page would also have to say "this number already has an account", which tells a stranger that this student uses the food bank. At the counter, a volunteer has seen the real MUN card, so every account belongs to a real card holder.

Our own website makes the setup code. MUN isn't involved. The volunteer never sees the password. R1 R2

Logging in

To book, view or cancel, the student logs in with their ID number and password. P6

The password is saved only as a hash, never as text. P8 Many students will reuse their MUN password. If our database leaked, plain passwords would expose their MUN accounts too. The setup page asks them not to reuse it.

Wrong passwords: at most 5 tries per 15 minutes for each ID number. After that, the student has to wait. P9 We slow tries down instead of locking the account, because otherwise anyone could lock a student out on purpose just by typing wrong passwords for their number.

Forgot the password?

The student goes to the counter and the volunteer presses "New setup code". The steps are the same as above. There's no email (we don't store one) and no recovery code. A recovery code is one more thing for students to keep, and anyone who found it could take over the account.

The costs: a first-time student can't book online, so their first visit has to be in person. And a student who forgets their password on booking night can't book until they reach the counter. They can walk in and reset it there. Known issue A MUN-email reset would fix this, if MUN ever gives access.

How much can a student take?

Each booking is for one person. I3

  • Up to 13 items (a sample number). "Up to", not "exactly": students shouldn't be forced to take food they won't use.
  • One of each item, counting all its varieties together. So one canned chicken, not one chunk chicken and one chicken in broth, even if there's plenty.

Extras

Extras are things like eggs, bread and chips. They change too often to book online and don't count toward the item limit. E1 The app shows today's extras as "may be available". E2 The student asks for them at pickup and gets at most one of each extra item. E3 The volunteer records what was given, and the pickup screen allows only one of each. E4

Volunteers or the coordinator update the items and stock counts before each booking window opens, for example to add new donations. Bookings already made keep the items they booked. I8 Since walk-ins are recorded too (section 13), the count stays right between updates.

7When booking is open

Pickup: Monday and Thursday, 3:30–5:30 pm, in 10-minute slots. S1 The food bank is closed on the other days.

Booking for a pickup day is open from 5 pm the day before until 12 pm on the day. All of that day's slots open at the same time. S5 Cancelling is allowed until 12 pm too. S6

Pickup dayBooking opensBooking and cancelling closePackingPickup
MondaySunday 5 pmMonday 12 pmMonday 12–3 pmMonday 3:30–5:30 pm
ThursdayWednesday 5 pmThursday 12 pmThursday 12–3 pmThursday 3:30–5:30 pm

Why 5 pm the day before? Students with daytime classes can book in the evening. And booking close to pickup means the stock students see is close to what's really on the shelf.

Why stay open overnight? No pickups happen between 5 pm and noon the next day, so the stock doesn't change. Staying open costs nothing in accuracy, and students who are busy in the evening can book at 9 pm or 7 am.

Why close at 12 pm? So volunteers have every order before they start packing.

The cost: slots go to whoever is free at 5 pm. Most of the university is done by then. Known issue We'll look again if MUN gets involved.

8How many students per slot

3:30–5:30 is 12 slots of 10 minutes. For now, one student per slot, so 12 online bookings per pickup day. S2 It's a setting, so it can change without touching the code.

Example Monday

bookedfree

10 of the 12 slots are booked. 4:30 and 5:20 are still free.

  • Walk-ins don't use slots. They have their own line with their own volunteers (section 13). W3
  • If slots fill up quickly every week and the counter has spare time, the number per slot can go up to 2 (24 a day). Bags are already packed, so a pickup only takes a few minutes.

No daily limit. The system only controls online bookings, and the slots already limit those to 12 a day. Walk-ins come as they come. The aim is to move everyone to booking online over time. Decided

9Step 2: Making a booking

What the student does

1Logs in with their ID number and password.
↓
2Picks a pickup day that's open for booking.
↓
3Picks a free 10-minute slot. The system first checks they're allowed to book (30 days, no other booking, didn't cancel for this day), then holds the slot while they choose. One held slot at a time. S8
↓
4Chooses items: up to 13, one of each item.
↓
5Ranks up to 5 substitutes (see section 12).
↓
6Presses Book. After this, the items can't be changed. I7

What the system checks when they press Book

ONE TRANSACTION: ALL OF THIS HAPPENS, OR NONE OF IT
Is booking open for this day right now (5 pm the day before until 12 pm)? S5
↓
Has it been 30 days since their last pickup? F1
↓
Do they have no other upcoming booking? F2
↓
Lock the slot. Is it still held for them? S2 S8
↓
Is every chosen variety in stock? Take each one off the stock count. I4 I5
↓ all yes
Saved as Booked. The student sees their booking code.
or
If any check fails, nothing is saved and the student sees why.

An example: Ana books for Monday

  • Sunday 5:02 pm. Ana picks the 3:40 slot. It's held for her, so nobody else can take it while she chooses.
  • 5:02–5:08. She chooses her items (like sunflower oil) and her substitutes. Nothing is taken from stock yet.
  • 5:08. She presses Book. The system turns her held slot into a booking, takes her items off the stock count (sunflower oil 6 → 5), and saves the booking with a booking code.

What's a transaction? A group of database changes that either all happen or none happen. If the server crashed halfway through Ana's booking, without a transaction she might have a booking while her sunflower oil still looks free to others. With a transaction, the crash undoes everything and she just presses Book again.

Why are items reserved only when she presses Book? I5 If choosing held stock, students who added oil to their list and then closed the app would make the oil look gone, and nobody would get it. The downside: if someone books the last bottle while Ana is choosing, her Book says "Sunflower oil just ran out, please choose something else". Nothing else about her booking is lost.

Why hold the slot? Without it, someone could take 3:40 while Ana is still choosing, and she'd have to start again.

Pressing Book twice (a double-tap, or slow Wi-Fi) still makes only one booking and takes one bottle of oil. B4

The hold lasts 10 minutes, with a countdown on screen: "3:40 is held for you: 7 minutes left". If time runs out, the slot is free again straight away, and Ana starts over like everyone else. S8

10The 30-day rule

  • A pickup must be at least 30 days after the person's last pickup. F1
  • A person can have only one upcoming booking at a time. F2
  • Cancellations, whether by the student or the food bank, don't count. F3
  • No-shows don't count either. This is a setting the food bank can change.
  • Walk-ins do count, because they're recorded in the same system. W1 Otherwise someone could walk in one week and book online the next.

How the days are counted: calendar days in Newfoundland time, from the date of the last pickup to the date of the new slot. The time of day doesn't matter. So after a pickup on Thursday 1 October at 5 pm, the 30 days end on Saturday 31 October, and the first slot they can book is Monday 2 November at 3:30 pm. With pickups on Mondays and Thursdays, the wait is 31 or 32 days in practice. Decided

Why don't no-shows count? People miss pickups for many reasons, and a penalty hurts the people who need food most.

11Step 3: Cancelling

  • No changes: once a booking is made, its items and substitutes can't be changed. I7
  • Cancel: the student can cancel until 12 pm on the pickup day. S6 Booking is still open until then, so the slot and the items go straight back for someone else to book. I6
  • A cancelled booking doesn't count toward the 30 days. F3
  • No booking again that day: a student who cancels can't book again for that same pickup day. Otherwise cancelling and booking again would be a way to change items. They can book a later pickup day. S6
  • After 12 pm there's no cancel button, because the bags are being packed. If the student doesn't come, it becomes a no-show at 6 pm (section 14).

12Step 4: Packing and substitutes

On the pickup day, from 12 pm (when booking closes) until 3 pm, volunteers pack the bags. K1 They see a packing queue: each booking shows its booking code and items, never the ID number. R2 P4 Every list is final by then, so nothing changes while they pack.

Why can something run out if it was reserved?

The stock count on screen can be wrong: a box was damaged, something expired, or it was counted wrong. So a volunteer may reach for sunflower oil and find none.

Why substitutes?

If something has run out, the volunteer swaps in a substitute while packing, so nobody has to decide at the counter. That saves time for both students and volunteers.

The rules

  • The student chooses a variety, like sunflower oil. Any brand or size of sunflower oil counts as sunflower oil. U1
  • A different variety, like peanut oil, is never given in its place unless the student listed it as a substitute. U1 U5 Only the student knows their allergies: someone who picked gluten-free pasta never gets regular pasta.
  • Up to 5 substitutes, ranked in order. A substitute can be any variety that isn't an extra and isn't already in the order. U2
  • Substitutes are not reserved. U3 Holding 5 more items per student would block food that usually isn't needed. The cost: a substitute may also be gone by packing time.
  • Refill rule: missing items are refilled from the substitute list in rank order. A substitute is skipped if it's out of stock, or if it would give the student a second of the same item. Refilling stops when the bag is back to its original size. U4
  • If every substitute is gone too, the volunteer asks the student at the counter to choose from what's on the shelf, within the same limits, and records it. This should be rare with 5 substitutes. U6
  • Every swap is written on a sticky note on the bag, so the student sees what changed. U8
  • When a volunteer marks a variety as out of stock, every other booking that reserved it is flagged in the packing queue, so the next volunteer knows before they start. U7

13Step 5: Pickup at the counter

From 3:30 to 5:30 there are two lines side by side, each with its own volunteers. W3 One hands out bags that were booked online. The other serves walk-ins. Most students are expected to move to booking online over time.

Booking online doesn't prove the student is eligible. The check at the counter does. P5

14The life of a booking

Every booking is in exactly one status. It can only move along the arrows. B1 B2

The three boxes with thick borders are the end. The only move between them is the dashed line: a volunteer fixing a mistake, which is logged. B6 The system marks no-shows by itself at 6 pm, which gives volunteers half an hour after closing to finish marking bags picked up. A booking that was never packed also becomes a no-show at 6 pm. Any other move is refused, so a cancelled booking can't be marked picked up. B2 B3 I6

  • Snow day after packing: the bookings are cancelled and the items go back into the stock count, so volunteers unpack the bags to make the shelf match. S7
  • No-show: volunteers put that bag's items back on the shelf. Keeping "no-show" separate from "cancelled" lets the food bank see how many slots are wasted.

15What the coordinator does

  • Items and stock: updates the item list each week. Bookings already made keep their items. I8
  • Settings: changes the numbers (30 days, slot capacity, booking times…) without touching the code.
  • Closing a day: for a holiday, bad weather or the Christmas break. Every booking that day is cancelled, even packed ones, and the items go back to stock. Those students can book again, because cancellations don't count. S7 F3
    Known issue We have no contact details, so we can't tell students their day was closed. MUN email might fix this if MUN approves the project.
  • Volunteer accounts: creates them with a username (a first name or nickname) and gives each volunteer a one-time setup code. The volunteer sets their own password with it, the same way students do, so the coordinator never sees it. A volunteer who also uses the food bank has a separate student account. The first coordinator account is made by a setup script when the system is installed. R3 R4
  • Moving booking times: if the website is down on booking night, the coordinator can open booking later or keep it open longer for that one day. S9
  • Totals only: pickups per week, items given out, no-shows. Never who picked up. Numbers under 5 show as "fewer than 5". P12

16Data over time, and time zones

  • 90 days: booking details are deleted after the retention period. Only totals are kept. P7 (See the timeline in section 10.)
  • Time zones: every time is stored in UTC and shown in Newfoundland time. T1 Newfoundland is UTC−3:30 in winter and UTC−2:30 in summer. A UTC time never jumps when the clocks change. We convert only when showing it on screen.

Accounts with no pickup for a year are deleted. P13

17When two people book at the same moment

A lock on a database row means "I'm using this, wait until I'm done". Here's what happens when two students tap the free 4:00 slot at the same moment:

WhenStudent AStudent B
5:01:00 pmTaps the 4:00 slot (it's free)Taps the same slot
a moment laterLocks the 4:00 slotTries to lock it → has to wait
a moment laterIt's free → held for A. Lock released.(still waiting)
a moment laterGets the lock, sees it's held → "This slot was just taken. Please pick another."

Without the lock, both would see "free" and both would get 4:00: two students in a one-student slot. The same idea stops two students taking the last tin of chicken: stock can never go below zero. S2 I4

Why lock things in a fixed order? A booking locks several rows: its slot and the stock of each variety. Suppose booking 1 locked oats and then wanted rice, while booking 2 locked rice and then wanted oats. Each would wait for the other forever. That's called a deadlock. If every booking locks rows in the same order, it can't happen. We'll fix the exact order when we design the tables.
