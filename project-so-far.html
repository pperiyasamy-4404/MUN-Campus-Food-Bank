1What we're building

The Campus Food Bank at Memorial University gives free food to students. We're building a website for it. With it, a student can:

  • choose a 10-minute pickup time on a Monday or Thursday afternoon,
  • choose up to 13 things from what's on the shelf, like oats, pasta or canned chicken,
  • list up to 5 substitutes, in case something runs out before their bag is packed,
  • get a short booking code like K3P to say at the counter.

Volunteers pack the bags before pickup starts and hand them over. A coordinator runs the food bank and its settings.

Two promises shape everything

Fair

Each student can pick up once every 28 days. The system checks this, so nobody has to remember faces or keep a paper list F1.

Private

The system never stores a student's name, email or phone number. It doesn't even store their MUN ID number. Volunteers only ever see the booking code and the food P2 P3 P4.

It's a prototype. Everything uses made-up data. Nothing is live. The food bank hasn't agreed to anything yet, and the real rules will be agreed with them later.

4The four pieces, and how they talk

The pages: React + TypeScript

What people see and click. React builds a screen out of small pieces called components. When the data changes, like the 10-minute countdown, React redraws only what changed. TypeScript is JavaScript with types, so a typo like booking.cod is caught before the page runs. Vite runs the pages while we work on them.

The pages decide nothing important. Anyone can change what runs in their own browser, so every rule is checked again on the server.

The server: Python + FastAPI

Each web address, like POST /api/bookings, is a short Python function in app/routes/. It checks the request has the right shape, then calls the rules in app/services/. Keeping the rules apart from the web part means a test can check a rule directly.

The database: PostgreSQL

Keeps everything: accounts, food, days, bookings. SQLAlchemy lets Python treat each table as a class and each row as an object. Alembic keeps a numbered history of every change to the tables (a migration), so the same database can be built again anywhere.

The tests: pytest

358 small programs that each check one thing, like "a 14th item is refused". They run against a real PostgreSQL test database, never the working one. Each test is undone when it ends, so tests can't affect each other.

Why one website, not two? While we work, the pages live at localhost:5173 and the server at localhost:8000. Vite passes every /api request on to the server, so the browser thinks it's all one site. The login cookie then works with its strictest safety settings, and we need no extra setup for two sites talking to each other.

5One click, followed all the way

A student has chosen quick oats and penne, with rice as a substitute, and presses Book. Here's everything that happens, in about a tenth of a second:

  1. The page (ChooseFood.tsx) sends POST /api/bookings with {"items": [{"variety_id": 4}, {"variety_id": 7}], "substitutes": [9]}. The browser adds the login cookie by itself.
  2. FastAPI checks the request has the right shape. A list of numbers? Good. Then it finds who's logged in from the cookie. Not a student? "Please log in." The route's own code never runs.
  3. The route (routes/booking.py) calls book() in services/booking.py.
  4. The rules: lock the time, check the 10 minutes haven't run out, check the 28 days and the other rules again, check the food limits, take a place, take the food off stock.
  5. The database saves the booking, its food and its substitutes, all together or not at all.
  6. The answer goes back: {"code": "K3P", "status": "booked", ...}.
  7. The page shows "Your code is K3P", with the food and a Cancel button.

If anything in step 4 refuses, nothing is saved and the student reads why, like "Sorry, Penne has just run out. Choose something else." Their list stays on the screen.

10Five ideas that hold it together

1. The ID number is never saved, only a keyed hash

A hash turns a value into a fixed-looking jumble. The same value always gives the same jumble, but you can't turn the jumble back. A keyed hash (HMAC) mixes in a secret key first:

202312345  + secret key  →  3f9a7c...e21b   (64 characters)
202312345  + secret key  →  3f9a7c...e21b   ← same card, same answer: the counter can find the account
202312345  + wrong key   →  91c04d...7a3f   ← without the key, nobody can match a number

ID numbers are only 9 digits, so without a key, someone with a copy of the database could try all billion numbers in minutes. The key lives in backend/.env, outside the database, so a stolen database alone gives nothing P2 P11. Passwords use a different, deliberately slow hash called argon2 P8.

2. The database is the last guard

The code checks every rule and says what's wrong in words. But code can have bugs. So the most important rules are also database rules that refuse bad data, whatever the code does:

CHECK (stock >= 0)                    -- I4: never less than none
CHECK (booked_count <= capacity)      -- S2: never more students than places
UNIQUE (student_id) WHERE status IN ('booked', 'packed')
                                      -- F2, B4: one upcoming booking per student

Each database rule has a name, and a test checks that the right one refuses.

3. Locks, for "at the same moment"

At 5:00 pm many students press Book together. Say there's one tin left:

Without a lock:
  Ana reads "1 left"      Ben reads "1 left"
  Ana takes it: 0 left    Ben takes it: -1 left, or two bags promised one tin

With a lock:
  Ana locks the tin's row, reads "1 left", takes it, saves, lets go
  Ben was waiting. Now he reads "0 left" and sees "Sorry, it has just run out."

Locks are always taken in the same order: the time, then the hold or booking, then the food from the lowest number up. If two people locked things in a different order, each could end up waiting for the other forever (a deadlock).

4. All or nothing

Pressing Book changes four tables. A transaction makes them one change: either everything is saved, or nothing is. If the 9th of 9 foods has run out, the place and the first 8 foods are given back by themselves. Nobody has to write code to undo each step.

5. A test for every rule

Every rule has at least one test, written as an example: "a student who picked up on 12 October can't book 8 November". The "at the same moment" tests really use two database connections at once. For the most important ones, we took the protection out on purpose and watched the test fail. That proves the test can catch the problem, not just pass.

And one habit: every refusal says why, and what to do. Not "Error 409", but "Booking for Monday, November 9 opens Sunday, November 8 at 5:00 p.m." or "Your next pickup can be on Tuesday, November 10 or later."

11A booking's life

Every booking has a status. Only these moves are allowed B1 B2:

A cancelled booking can never become picked up, for example. One more move isn't drawn: a volunteer can undo Packed on the wrong bag, which takes it from packed back to booked, until it's handed over. A day the coordinator closes cancels every booking on it too S7. That's step 9.

Food moves with the status. Booking takes it off stock. Cancelling or a no-show puts it back I5 I6.

13How to run it

Each server needs its own terminal. The folder name has a space, so keep the quotes.

# Terminal 1: the server
cd "D:\MUN Project\backend"
.venv\Scripts\python -m uvicorn app.main:app --reload

# Terminal 2: the pages
cd "D:\MUN Project\frontend"
npm run dev

Then open http://localhost:5173.

Your working database has no coordinator yet. Make one in a third terminal, then go to /staff/setup and use the code it prints:

cd "D:\MUN Project\backend"
.venv\Scripts\python -m app.first_coordinator YourName

To run the tests (about 30 seconds):

cd "D:\MUN Project\backend"
.venv\Scripts\python -m pytest

Booking for a sample day only opens at 5 pm the day before it. To try booking sooner, a day has to be opened early. That's the coordinator's job in step 9. Until then, ask me and I'll open one. The same goes for packing and the counter: ask me and I'll set up today as a pickup day with a few bags.

15Words used on this page

Frontend
The part people see and click: the pages in the browser.
Backend, server
The program that keeps the rules and talks to the database.
Address, endpoint
A web address the server answers, like GET /api/stock. GET asks for something, POST sends something.
JSON
The text format the pages and the server send each other, like {"code": "K3P"}.
Route
The Python function that answers one address.
Service
The Python code that holds the rules. Routes call services.
Component
A small piece of a React page, like the countdown or the food list.
Table, row, column
How the database keeps things: like a spreadsheet.
Database rule
A rule the database itself enforces, like CHECK (stock >= 0) or UNIQUE.
Migration
One numbered change to the tables, kept as a file, so any database can be brought up to date.
Transaction
A group of changes saved together, or not at all.
Lock
"Wait, I'm using this row." Others wait until the transaction ends.
Hash
A one-way jumble of a value. The same value gives the same jumble.
HMAC, keyed hash
A hash mixed with a secret key, so only someone with the key can make one.
Session, cookie
After logging in, the browser keeps a random ticket (the cookie). The server keeps a hash of it (the session) and knows who you are from it.
Setup code
A one-time code like K7QM-4TXP, given in person, used to choose a password.
Hold
A time kept for one student for 10 minutes while they choose food.
Variety
One kind of an item, like quick oats. Stock is counted per variety.
Substitute
Food the student would take instead, if something they booked is missing.
Extra
Food like bread or eggs, given at the counter, not booked online.
Walk-in
A student who comes without a booking.
No-show
A booking nobody came for by 6 pm.
Test
A small program that checks one thing and fails loudly if it's wrong.
