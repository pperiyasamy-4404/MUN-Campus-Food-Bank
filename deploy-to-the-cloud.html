Putting the app on the cloud, for free

Right now the app only runs on your laptop, so only you can use it. This page shows how to put it on a computer on the internet (a "server" in "the cloud") so students and volunteers can open it on their phones from anywhere. Every step, in order, with the exact commands, and $0 a month.

The short version. Rent a free computer from Oracle Cloud in Toronto. Put the database, the app and a "front door" program on it. Give it a free web address. Tell it to run the jobs every 15 minutes. About 2 to 3 hours the first time.

Before real students use it: the Campus Food Bank (and probably MUN) must agree. Until then, put it online with made-up data only, to show people. Part 14 lists what to check first.

1The big picture

On your laptop, you run two programs in two terminals: the server and the pages. On the cloud it's one computer that runs four things by itself, day and night:

Why the pages and the app share one address: the login cookie only works when both come from the same website (it's "SameSite=Strict", accounts.html part 5). On your laptop, Vite passes /api to the app. On the server, Caddy does the same job.

2Which free cloud, and why

The load test showed what the server needs: at least 2 CPU cores (with 1 core, logins at 5 pm took up to 87 seconds), about 0.5 GB of memory, a database that is never deleted, and something that runs the jobs every 15 minutes. Most free plans fail one of these.

OptionFree?Good for this app?
Oracle Cloud "Always Free" server (our choice)Yes, no end dateYes. 2 cores and 12 GB of memory, a server in Toronto (data stays in Canada), and you can run anything on it, including the database and the 15-minute jobs.
Render, free planYesOnly for a quick demo. The app goes to sleep after 15 minutes with no visitors, and the first visit after that waits about a minute. The free database is deleted after 30 days. Very little CPU. Scheduled jobs are not free.
Heroku, with your GitHub Student Developer PackFree for 2 years (student credit)Simpler (no server to look after), but it ends when the credit does, and the servers are in the US or Europe, not Canada. A good plan B: ask me and I'll write those steps.
Azure for Students$100 credit a yearHas a Canada Central region, but the credit runs out, and you pay after that.
Your own laptopYesNo: it would have to stay on and online all the time, and home internet can't give it a proper address with HTTPS.

Why a whole server, not a "platform" that runs the app for you? The free platforms sleep, delete free databases, or charge for scheduled jobs. A server is more steps once, but then it's yours, always on, and $0.

Why not 4 cores? Oracle used to give 4 cores and 24 GB free. On 15 June 2026 it cut the free amount to 2 cores and 12 GB. 2 cores is what the load test asks for, so it's enough.

Two catches with Oracle's free server.

1. It asks for a credit card when you sign up, to check you're a real person. It doesn't charge it if you only use "Always Free" things. The steps below only use those.

2. Oracle may stop a free server that sits idle for a week (almost no CPU, network or memory used). A food bank app used twice a week could look idle. Oracle emails first, and a stopped server can be started again, but students would see nothing until then. The usual fix is to "upgrade" the account to Pay As You Go: the free things stay free, and Oracle doesn't stop idle servers. Then set a budget alert at $1 (step 1), so you'd hear about any charge at once. Check Oracle's Always Free page for the current rules before you rely on this.

3What you need before starting

  • An email address and a credit or debit card (for Oracle's check only).
  • Your GitHub account, with the MUN-Campus-Food-Bank repo (it's private, so the server needs a key to read it: step 8).
  • Your laptop with the project, and its PowerShell (Windows 11 has the ssh command built in).
  • A password manager, like Bitwarden (free), for two things you must never lose: the database password and the secret key.
  • 2 to 3 hours.

Where each step happens is marked like this: website you click in a web page, your laptop you type in PowerShell on your laptop, server you type on the cloud server (after logging in to it with ssh). Words in CAPITALS in a command are yours to fill in.

4All the steps, in one picture

5Steps 1 to 4: get a free server

Step 1. Sign up for Oracle Cloud website

  1. Go to oracle.com/cloud/free and press Start for free.
  2. For Home Region, choose Canada Southeast (Toronto). You can't change it later, and Toronto keeps the students' data in Canada.
  3. Give your card for the check. Wait for the "your account is ready" email (minutes to a few hours).
  4. Recommended: in the Oracle console, go to Billing > Upgrade and Manage Payment and choose Pay As You Go (see the catch in part 2). Then Billing > Budgets > Create Budget: $1 a month, with an email alert at 100%.

Step 2. Make the server website

  1. Menu Compute > Instances > Create instance. Name: foodbank.
  2. Image: Change image > Canonical Ubuntu 24.04.
  3. Shape: Change shape > Ampere > VM.Standard.A1.Flex, with 2 OCPUs and 12 GB memory. It should say "Always Free-eligible".
  4. SSH keys: choose "Generate a key pair for me" and press Save private key. Keep this file safe: it's the only way in. Save it as C:\Users\YOU\.ssh\foodbank.key.
  5. Press Create. When it says "Running", copy its Public IP address (like 155.248.12.34).

If it says "Out of capacity", Oracle has no free Arm servers left in Toronto right now. Try again later in the day, or the next day. It's common, and it passes.

Step 3. Open its doors website then server

Web pages arrive on two "ports": 80 (http) and 443 (https). Oracle keeps them shut until you open them, in two places.

  1. In the instance page, click its subnet, then the Default Security List, then Add Ingress Rules: Source CIDR 0.0.0.0/0, TCP, destination port 80. Add a second one for 443.
  2. The server itself also has a firewall. You'll open it in step 4, once you're logged in.

Step 4. Log in to the server your laptop

Windows wants the key file to be readable by you only. Then log in:

# Only you may read the key (once)
icacls $env:USERPROFILE\.ssh\foodbank.key /inheritance:r
icacls $env:USERPROFILE\.ssh\foodbank.key /grant:r "$($env:USERNAME):(R)"

# Log in. Answer "yes" the first time.
ssh -i $env:USERPROFILE\.ssh\foodbank.key ubuntu@PUBLIC_IP

The prompt changes to ubuntu@foodbank:~$. Everything typed now runs on the server. Open the server's own firewall for ports 80 and 443:

# server
sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 80 -j ACCEPT
sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 443 -j ACCEPT
sudo netfilter-persistent save
sudo apt update && sudo apt upgrade -y

Why two firewalls? Oracle's network (step 3) and the server's own (here). A request has to pass both, so both must say yes. The app and the database stay closed to the internet: only Caddy, on 80 and 443, is reachable.

6Step 5: a free web address

People can't be asked to type 155.248.12.34. And HTTPS (the padlock) needs a name. DuckDNS gives one for free.

  1. website Go to duckdns.org, sign in with GitHub.
  2. Type a name, like munfoodbank, and press add domain. Your address is munfoodbank.duckdns.org.
  3. In current ip, put the server's public IP and press update ip.

Later, MUN might give a nicer address, like foodbank.mun.ca. Then only step 12's first line changes.

7Steps 6 and 7: install the tools and the database

Step 6. Python 3.14, Node 24 and Caddy server

# Python 3.14, with uv (the same tool you use on your laptop)
curl -LsSf https://astral.sh/uv/install.sh | sh
source $HOME/.local/bin/env
uv python install 3.14

# Node 24, to build the pages
curl -fsSL https://deb.nodesource.com/setup_24.x | sudo -E bash -
sudo apt install -y nodejs git

# Caddy, the front door
sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https curl
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update && sudo apt install -y caddy

Step 7. PostgreSQL 18 and the app's database server

The same version as on your laptop, from PostgreSQL's own repository (Ubuntu's is older):

sudo apt install -y postgresql-common
sudo /usr/share/postgresql-common/pgdg/apt.postgresql.org.sh -y
sudo apt install -y postgresql-18

# Make up a long password and save it in your password manager first.
sudo -u postgres psql -c "CREATE ROLE foodbank_app LOGIN PASSWORD 'DATABASE_PASSWORD'"
sudo -u postgres createdb -O foodbank_app campus_food_bank

Why a separate login for the app, again? Same as on your laptop (tables.html): the app's login owns only its own database and has no admin powers. And PostgreSQL only listens inside the server, so nobody on the internet can even try that password.

8Steps 8 to 10: the code, the secret key, the tables

Step 8. Get the code from GitHub server and website

The repo is private, so the server gets its own read-only key (a "deploy key"). It can read this one repo and nothing else, and can't change anything.

ssh-keygen -t ed25519 -f ~/.ssh/github_deploy -N ""
cat ~/.ssh/github_deploy.pub

website Copy the line it prints. On GitHub: your repo > Settings > Deploy keys > Add deploy key. Title oracle server, paste, leave "Allow write access" off. Then:

cd ~
GIT_SSH_COMMAND="ssh -i ~/.ssh/github_deploy" git clone git@github.com:pperiyasamy-4404/MUN-Campus-Food-Bank.git
cd MUN-Campus-Food-Bank
git config core.sshCommand "ssh -i ~/.ssh/github_deploy"   # so "git pull" uses the key later

Step 9. Settings and the secret key server

cd ~/MUN-Campus-Food-Bank/backend
uv venv --python 3.14 .venv
uv pip install --python .venv/bin/python -r requirements.txt

# A new secret key for the live server. Copy it into your password manager too.
.venv/bin/python -c "import secrets; print(secrets.token_hex(32))"

nano .env

In the editor, type this (Ctrl+O, Enter to save, Ctrl+X to leave):

DATABASE_URL=postgresql+psycopg://foodbank_app:DATABASE_PASSWORD@localhost:5432/campus_food_bank
# Required by the settings, but never used on the live server: no tests run here.
TEST_DATABASE_URL=postgresql+psycopg://foodbank_app:DATABASE_PASSWORD@localhost:5432/not_used_on_the_live_server
SECRET_KEY=THE_KEY_IT_PRINTED
DB_CONNECTIONS=15
chmod 600 .env   # only you can read it

The secret key is the one thing you can never get back. Without it, no MUN card matches any account (P11). With it and a copy of the database, someone could work out ID numbers (P2). So: one copy in your password manager, never in GitHub, never next to the backups.

Use a new key for the live server, not your laptop's. Your laptop's key has been near made-up data and test runs.

Step 10. Tables, starting data, the first coordinator, the pages server

cd ~/MUN-Campus-Food-Bank/backend
.venv/bin/python -m alembic upgrade head          # make the 24 tables
.venv/bin/python -m app.sample_data               # the settings, the hours, sample food and photos
.venv/bin/python -m app.first_coordinator YOUR_NAME   # prints a setup code: keep it for step 15

cd ../frontend
npm ci
npm run build
sudo mkdir -p /var/www/foodbank
sudo rsync -a --delete dist/ /var/www/foodbank/

Why the sample data? The app needs its settings row and pickup hours to start. The sample food comes with it. The coordinator can hide sample food on the Stock page and add the food bank's real food. (When the food bank gives its real list, I can make a script for it instead.)

Never run these on the live server: app.dev_accounts (it makes accounts with the password "Password", and its "this computer only" check doesn't help here, because the live database is on the same computer), app.demo, pytest or the load test.

9Steps 11 and 12: run the app, with HTTPS

Step 11. The app, always on server

On your laptop you start the app in a terminal. On the server, Linux's service manager (systemd) starts it, restarts it if it ever stops, and starts it again after a reboot.

sudo tee /etc/systemd/system/foodbank.service > /dev/null <<'EOF'
[Unit]
Description=Campus Food Bank app
After=network.target postgresql.service

[Service]
User=ubuntu
WorkingDirectory=/home/ubuntu/MUN-Campus-Food-Bank/backend
ExecStart=/home/ubuntu/MUN-Campus-Food-Bank/backend/.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 2 --proxy-headers --forwarded-allow-ips 127.0.0.1
Restart=always

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now foodbank
sudo systemctl status foodbank      # should say "active (running)". Press q to leave.

Why --workers 2? One app process per CPU core. Each keeps up to 15 database connections, so 2 use 30 of PostgreSQL's 100.

Why 127.0.0.1? The app only listens inside the server. Only Caddy talks to it.

Step 12. Caddy and HTTPS server

Caddy gets a free HTTPS certificate by itself (from Let's Encrypt) and renews it. It sends /api/... to the app and everything else to the pages. It also adds the same safety headers the app sends, to the pages.

sudo tee /etc/caddy/Caddyfile > /dev/null <<'EOF'
munfoodbank.duckdns.org {
	encode zstd gzip

	header {
		Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'"
		X-Content-Type-Options "nosniff"
		X-Frame-Options "DENY"
		Referrer-Policy "same-origin"
		Permissions-Policy "camera=(), microphone=(), geolocation=(), payment=()"
		Strict-Transport-Security "max-age=31536000"
		-Server
	}

	handle /api/* {
		reverse_proxy 127.0.0.1:8000
	}

	handle {
		root * /var/www/foodbank
		@pages not path /assets/*
		header @pages Cache-Control "no-cache"
		try_files {path} /index.html
		file_server
	}
}
EOF

sudo systemctl reload caddy

Why "no-cache" on the pages but not on /assets? After an update, every phone must get the new index.html at once. The files in /assets have a new name each build (like index-Cl9Pl6aT.js), so they can be kept forever.

Why try_files ... /index.html? /book and /packing aren't files: they're React pages. Like the demo, every address that isn't a file gets index.html, and React shows the right page.

10Steps 13 and 14: the jobs and the backups

Step 13. The jobs, every 15 minutes server

This is "whoever hosts it runs python -m app.jobs every 15 minutes" from CONSTRAINTS.md: no-shows at 8 pm, pickup days a week ahead, deleting old details, tidying up. Linux's built-in timer, cron, does it:

crontab -e        # choose nano if it asks, then add this line at the bottom and save:

*/15 * * * * cd /home/ubuntu/MUN-Campus-Food-Bank/backend && .venv/bin/python -m app.jobs >> jobs.log 2>&1

*/15 * * * * means "every 15 minutes, every hour, every day". What each run did is added to backend/jobs.log, with numbers only, never a student.

Step 14. Backups, every night server

The 11 November decision was to use the cloud's own database backups. That was for a cloud database service. Here the database is on our own server, so nobody backs it up unless we do. The simplest safe way: every night at 3:30 am, PostgreSQL writes a copy, named by the weekday, so there are always 7 and the oldest is replaced.

sudo mkdir -p /var/backups/foodbank && sudo chown postgres /var/backups/foodbank
sudo -u postgres crontab -e        # add this line and save:

30 3 * * * pg_dump -Fc campus_food_bank > /var/backups/foodbank/foodbank-$(date +\%a).dump

A copy on the same server doesn't help if the whole server is lost. So once a week, also copy them to your laptop, or turn on Oracle's own boot volume backup (Storage > Boot Volumes > your volume > Backup policy). Oracle gives 5 volume backups free.

# your laptop, once a week
scp -i $env:USERPROFILE\.ssh\foodbank.key ubuntu@PUBLIC_IP:/var/backups/foodbank/*.dump D:\foodbank-backups\

A backup only counts once you've restored it once. Try it on your laptop with pg_restore into an empty database, before real students. Keep the secret key apart from these files (part 8).

11Step 15: check it works

  1. On your phone, open https://munfoodbank.duckdns.org. You should see the logo and the pickup days, with the padlock.
  2. Go to /staff/setup and use the setup code from step 10 to choose your coordinator password.
  3. On the Counter page, give a made-up student a setup code (a made-up 9-digit number), set them up in a private window, and book.
  4. server After 15 minutes, tail ~/MUN-Campus-Food-Bank/backend/jobs.log shows a jobs run.
  5. website Optional, free: on uptimerobot.com, add a monitor for https://munfoodbank.duckdns.org/api/pickup-days. It emails you if the site is ever down.

12Changing the app later

After you push a change to GitHub (and GitHub Actions shows it green), put it on the server:

# server
cd ~/MUN-Campus-Food-Bank && git pull
cd backend && uv pip install --python .venv/bin/python -r requirements.txt
.venv/bin/python -m alembic upgrade head          # only does something if the tables changed
cd ../frontend && npm ci && npm run build && sudo rsync -a --delete dist/ /var/www/foodbank/
sudo systemctl restart foodbank

Do it outside busy times: not between 5 pm (booking opens) and 8 pm on a pickup day. The restart takes a few seconds.

13If something goes wrong

What you seeWhere to look

"Something went wrong on our side"~/MUN-Campus-Food-Bank/backend/errors.log: every server error, with its traceback, never anything a person typed

14Before real students use it

Everything above can be done now, with made-up data, to show people. Real students need more:

  1. The Campus Food Bank agrees, and answers the open questions in CONSTRAINTS.md. MUN's privacy office may want to know what's stored: no names, emails or phone numbers, only a keyed hash of the card number, in Toronto.
  2. A new database and a new secret key for the real thing, with none of the made-up students in it.
  3. Their real food list on the Stock page.
  4. A load test on this server. The load test is written for Windows today (how it stops processes and measures memory). It needs small changes to run on Linux. Ask me then. It matters, because on Windows 4 processes sometimes left a quarter of the logins unanswered, and this server runs 2.
  5. A restored backup, tried once (part 10).
  6. Someone besides you who can log in to the server, with the key and the secret key, in case you're away.

15Words used on this page

WordMeaning
