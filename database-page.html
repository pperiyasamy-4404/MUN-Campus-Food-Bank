The first page that reads the database

Until today the app only said hello. Now the page shows the real pickup days, their 10-minute slots and the food, straight from PostgreSQL. Nothing can be booked yet. This page explains how it works, piece by piece, and why each piece is built the way it is.

1The journey of one request

When the page opens, React asks the server for the pickup days. Here is every stop that question makes, there and back.

2The two new addresses

An address (also called an endpoint) is a URL the server answers. We have two, and both only read. Nothing in them can change the database.

GET /api/pickup-days

Today's pickup day, if there is one, and every one after it. Each day comes with its slots.

[{
  "pickup_date": "2026-11-09",
  "booking_opens_at": "2026-11-08T17:00:00-03:30",
  "booking_closes_at": "2026-11-09T12:00:00-03:30",
  "booking_status": "not_open_yet",
  "closed_reason": null,
  "slots": [
    {"starts_at": "2026-11-09T15:30:00-03:30",
     "places_left": 1},
    ... 11 more
  ]
}]

GET /api/food

The food on the list, A to Z, in two parts: food you book, and extras.

{
  "bookable": [{
    "name": "Breakfast",
    "items": [{
      "name": "Oats",
      "varieties": [
        {"name": "Quick oats", "stock": 14,
         "tags": ["Vegetarian"]}
      ]}]}],
  "extras": [{
    "name": "Bakery", "items": [{
      "name": "Bread", "varieties": [
        {"name": "White bread", "stock": null,
         "tags": ["Vegetarian"]}]}]}]
}

Short version: the server sends plain data (JSON). React decides how it looks. So later a phone app, or the volunteer screen, could use the same addresses.

The old /api/hello address is gone, with its test. It was only there to prove the two halves could talk, and these two addresses prove that now.

3Dependencies: db and now

Look at how the pickup-days route starts:

@router.get("/pickup-days")
def upcoming_pickup_days(db: DB, now: Now) -> list[PickupDayOut]:

The route doesn't open a database session or read the clock itself. It asks for them, and FastAPI hands them over. A thing a route asks for like this is called a dependency. Both live in app/deps.py:

def get_db():
    """One database session per request, closed when the answer has been sent."""
    with SessionLocal() as db:
        yield db

def get_now():
    return datetime.now(UTC)

DB = Annotated[Session, Depends(get_db)]    # "a Session, made by get_db"
Now = Annotated[datetime, Depends(get_now)]

Why: a test can swap them. The test client says "use this test's session instead", so the route reads the rows the test just made, and they're undone afterwards. And a test can stop the clock at, say, Sunday 8 November at 5:00 pm, to check that booking opens exactly then.

Why not make the session inside the route? Then every test would hit the working database, and the sample data would get mixed up with test data.

Why not call datetime.now() inside? Then a test about "booking opens at 5 pm on Sunday" could only pass if you ran it at 5 pm on a Sunday.

4Response models: the shape of the answer

Each route says exactly what its answer looks like, as a small class:

class SlotOut(BaseModel):
    starts_at: datetime
    places_left: int

The route builds SlotOut objects, and FastAPI turns them into JSON. Only the fields listed here go out. A slot row in the database also has id, pickup_day_id, capacity and booked_count, and none of those reach the browser.

Why: nothing leaves the server by accident. This matters a lot from step 3 on: a student row has an id_hash, and rule P10 says the ID must never show up anywhere. If routes sent whole rows, one forgotten column would leak it. With response models, a field has to be written down on purpose to go out.

Bonus: FastAPI builds a page from these classes. Start the server and open http://localhost:8000/docs to see both addresses and try them.

Why not send the database rows directly? They'd send every column, and their shape would change whenever a table changes, breaking the page.

The TypeScript side has the same shapes, in frontend/src/api.ts. They're written by hand for now, so if one side changes, the other must change too.

5Times: Newfoundland, always

Rule T1: times are stored in UTC and shown in Newfoundland time. Here's the whole trip of one slot's start time:

WhereWhat it looks like
In the database (one exact moment)2026-11-09 19:00 UTC
Sent by the server2026-11-09T15:30:00-03:30: the same moment, written in Newfoundland time. The -03:30 says how far from UTC it is.
Shown on the page3:30 p.m.

The page uses the browser's built-in date formatter, told to use America/St_Johns. So a student whose laptop is still set to Toronto time still sees 3:30 p.m., not 2:00 p.m.

The trap with dates that have no time

A pickup date like "2026-11-09" has no time of day. To format it, JavaScript has to pick one, and it picks midnight UTC. Midnight UTC is 8:30 pm the evening before in St. John's, so:

Shown in Newfoundland time:  Sunday, November 8     ← wrong day!
Shown in UTC:                Monday, November 9     ← right

So dates are shown in UTC and moments in Newfoundland time. Both lines above were really printed while building this, to be sure.

What "today" means

The server leaves out days that are over. But at 11 pm on Thursday in St. John's, it's already Friday in UTC. If "today" came from UTC, Thursday would vanish from the list an hour and a half early. So the server turns the moment into a Newfoundland date first:

today = now.astimezone(NEWFOUNDLAND).date()

6Booking status, on the dot

Each day gets one of four statuses, worked out from the clock. The function is booking_status in app/services/pickup_days.py, so step 5 (booking) can use the very same rule.

Moment (for Monday 9 November)StatusOn the page
Sunday 4:59 pmnot_open_yetBooking not open yet
Sunday 5:00 pm exactlyopenBooking open
Monday 11:59 amopenBooking open
Monday 12:00 pm exactlybooking_overBooking over
Any time, if the coordinator closed the dayday_closedDay closed, with the reason

Why the server works it out, not the browser: the browser's clock can be wrong, and the server is what will refuse a booking after 12 pm anyway. One clock decides.

Why "on the dot" matters: rule S5 says booking opens at 5 pm. A test checks 4:59 and 5:00, and 11:59 and 12:00, so nobody can "fix" it to <= by mistake.

7The food list: two questions, not forty

The sample data has 17 varieties, and most have tags. The simple way to build the list asks the database once for the varieties, then once more for each variety to get its tags: 18 questions. With 40 varieties it's 41. This is a well-known slow pattern, called the N+1 problem.

Instead the route asks two questions: one for every variety with its item and category, already sorted A to Z, and one for every tag of those varieties. Then Python sorts them into groups. Same for slots: one question for all the days' slots, not one per day.

Three rules the list follows

  • Hidden varieties are left out. When the food bank stops getting something, it's hidden (active = false), not deleted, because old bookings still point to it. An item whose varieties are all hidden disappears, and so does an empty category.
  • Extras have no count. Rule E2 says extras show only as "may be available". The server sends "stock": null for them, so the browser never even gets the number.
  • Out of stock still shows. Bookable food with 0 left is listed as "Out of stock", so students can see it exists and may come back.

8The React side

FileWhat it does
api.tsThe shapes the server sends, and useServerData: "ask the server for this once, and tell me if it's loading, ready or failed".
time.tsThe three formatters: 3:30 p.m., Sunday, November 8 at 5:00 p.m. and Monday, November 9.
PickupDayList.tsxA card per day, with its status badge and a tile per slot.
FoodList.tsxA card per category, then items, then varieties with their tags and stock.
App.tsxPuts the two lists on the page.

The loading state has three cases, written as a TypeScript type:

type ServerData<T> =
  | { state: 'loading' }
  | { state: 'ready'; data: T }
  | { state: 'failed' }

Why this shape: TypeScript won't let the page touch data unless the state is 'ready'. So "the page crashed because the data wasn't there yet" can't happen.

Why not a data-fetching library (like TanStack Query)? It adds caching and refetching, which is useful later when screens change data. For two read-only lists, 30 lines we can read is better than a library we'd have to learn first.

The page follows the computer's light or dark setting, using the CSS light-dark() function for each colour.

9The tests

19 new tests, and the hello test gone: 99 in all. The test client asks the server questions just like the browser does, but in memory, with the test database.

FileChecks
test_pickup_days_api.pyTimes come out in Newfoundland time, in winter (-03:30) and summer (-02:30). Past days are left out, today is kept. Today means today in Newfoundland, even at 11 pm. A booked slot has fewer places. A closed day says why. No days gives an empty list.

test_pickup_days.pyBooking status at 4:59, 5:00, 11:59, 12:00 and in the evening, and a closed day.

Two small helpers make these possible: the client fixture in conftest.py (the server uses the test's session) and stop_the_clock_at(moment) in helpers.py.

Do the tests really catch mistakes? Two bugs were put in on purpose, then taken out: "today" taken from UTC, and booking still open at 12:00 exactly. The suite failed on both, with the right test each time.

10Not done yet, and one open question

  • Places left ignores holds. It counts bookings only. Holds (a slot kept for 10 minutes while a student chooses, S8) come with booking in step 5, and then "places left" will take them off too.
  • Anyone can open this page. It shows no personal data, only dates, times and food. Once accounts exist (step 3), we decide which screens need a login.
  • This is a look-around page, not a student screen. The real booking screens come in step 5 and will reuse these two addresses.

Open question: should students see exact counts like "6 left", or just "available" and "out of stock"? The rules don't say. Exact counts help students choose, but they may make people rush for the last one. This page shows exact counts for now, because it's for us. It's a question for the food bank, and a one-line change either way.

11How to run it

Two terminals, same as before. The folder name has a space, so keep the quotes.

# terminal 1: the server
cd "D:\MUN Project\backend"
.venv\Scripts\python -m uvicorn app.main:app --reload

# terminal 2: the page
cd "D:\MUN Project\frontend"
npm run dev
